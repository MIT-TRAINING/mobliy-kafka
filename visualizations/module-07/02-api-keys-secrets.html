API keys & secrets management (Confluent Cloud)

On Confluent Cloud, every Kafka client authenticates with an API key and secret. The key acts with the permissions of its owner, a user or a service account. billing-svc is running on the personal key that you, l07, created in Module 6. Move it to a service-account key with zero failed requests. Then leak the secret and rotate it the same way. To see how outages happen, delete a key while the app still uses it.

Rotating a key without downtime

  1. 1confluent api-key create --resource lkc-9p3kd --service-account sa-r7k2p9 --description "billing-svc 2026-10"
  2. 2Put the new secret in the secrets manager, not in the repo and not in a ticket.
  3. 3Wait a minute or two: new keys take a short time to become usable. Then roll the app.
  4. 4Verify: no SaslAuthenticationException in the app logs, and consumer lag is stable.
  5. 5confluent api-key delete <OLD_KEY> --force. Both keys worked in parallel until now.

What the client uses

bootstrap.servers=pkc-xxxxx.ap-south-1.aws.confluent.cloud:9092
security.protocol=SASL_SSL
sasl.mechanism=PLAIN
sasl.jaas.config=org.apache.kafka.common.security.plain.PlainLoginModule \
  required username="<API_KEY>" password="<API_SECRET>";

The key is the SASL username and the secret is the password. TLS is always on. Render this file at deploy time from the secrets manager, owned by the app user with mode 0600.

Admin takeaway: production apps get service-account keys. A user-owned key has the user's permissions (yours are EnvironmentAdmin), and it is deleted when the user is removed from the organization. Check owners with confluent api-key list --resource lkc-9p3kd.
Security gotcha: an API key only proves who the client is. A brand-new service-account key with no role bindings authenticates successfully, but every produce and fetch fails with TOPIC_AUTHORIZATION_FAILED. Bind roles first (Topic 1).
