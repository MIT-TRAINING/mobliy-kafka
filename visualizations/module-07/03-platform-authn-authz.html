Topic 3

Confluent Platform authentication & authorization

Every request to the shared Platform cluster passes through the same checkpoints. First the TLS handshake on listener CLIENT :9092, then SASL/PLAIN with your LDAP password (authentication), then the Confluent Server Authorizer, which checks RBAC role bindings and ACLs (authorization). Pick a request and see which checkpoint stops it. Then switch LDAP off, or add an ACL, and send the same requests again.


    

  


  
Authentication: who are you?

  

    

      
MechanismIdentity comes fromOn the shared CP cluster

      
        
mTLS (ssl.client.auth=required)The client certificate's subjectControllers and the BROKER listener (:9091): brokers prove themselves with host certificates

        
SASL/PLAIN + LDAP callbackLDAP bind with username and passwordThe CLIENT listener (:9092), over TLS: learners l01…l18 and trainer

        
SASL/OAUTHBEARERA token from MDS or an OAuth/OIDC providerPlatform components such as Schema Registry, Connect and Control Center use MDS-issued tokens

        
SASL/SCRAM-SHA-512Credentials stored in the cluster metadataNot used here. It is what the shared Apache cluster uses (Topic 5)

        
SASL/GSSAPI (Kerberos)A Kerberos ticketNot used. Common in Active Directory shops

        
MDS login (HTTPS :8090)LDAP username and password, exchanged for a tokenconfluent login --url $MDS_URL, Control Center sign-in

      
    

  


  
Authorization: what may you do?

  

    
super.users
Broker config.
      These principals skip every check. Keep the list to brokers and the MDS super user, never people.

    
RBAC via MDS
Role bindings for users and
      LDAP groups (User:l07, Group:kafka-ops). They are stored in the _confluent-metadata-auth topic and cached on every broker.
      Roles include SystemAdmin, ClusterAdmin, UserAdmin, SecurityAdmin, AuditAdmin, Operator and the resource roles.

    
ACLs
Still supported next to RBAC, and needed for a few
      things RBAC doesn't cover. On the shared cluster, learners get Describe on the cluster as an ACL. A matching DENY ACL always wins.

  

  
Admin takeaway: read the error to find the checkpoint. PKIX path building failed
    → the client doesn't trust the CA. disconnected right after connecting → wrong security.protocol.
    SaslAuthenticationException → bad credentials or LDAP down. *_AUTHORIZATION_FAILED → login worked, so fix the role binding.

  
Production trap: with the LDAP callback, new logins depend on LDAP. If LDAP is down, connected clients
    keep running, but every restart and new consumer fails to authenticate. Run LDAP highly available, and use LDAPS. The lab's
    ldap://…:389 stays inside a private subnet, which is acceptable for a lab only.
