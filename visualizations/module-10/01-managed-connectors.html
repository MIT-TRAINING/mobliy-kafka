Confluent managed connectors: source and sink

A source connector brings data into Kafka from another system. A sink connector takes it out to another system. Both run as tasks on Connect workers. On Cloud, Confluent runs the workers and bills you per task-hour. On Platform, you or your platform team run them. Create the Datagen source (it stands in for the mediation feed) and an archive sink. Then raise the sink's tasks.max until it keeps up, inject a fault and fix it, and watch what the bill does.

Source connectors in a telecom shop

      
Mediation CDR files, the subscriber database (JDBC, or change data capture with
        Debezium), network probes over MQTT, legacy queues (IBM MQ source). The connector owns the read position in that
        system and writes records to a topic you created first.

    

    

      
Sink connectors

      
Archive CDRs to S3, push them to Elasticsearch for the NOC, write rated calls
        to the billing database. A sink is a consumer group named connect-<connector name>, so you watch
        its consumer lag exactly as you did in Module 9.

    

  


  
Admin gotcha: a connector can be RUNNING while its task is FAILED.
    The connector state only says the configuration was accepted. Read the task state and its trace, fix the
    cause, then restart the task. A failed task doesn't retry forever on its own, so alert on task state.

  
Production trap: tasks.max above the topic's partition count only adds
    idle sink tasks, and on Cloud each one is billed. Size it to the partitions. A sink can never use more tasks than the
    topic has partitions.
