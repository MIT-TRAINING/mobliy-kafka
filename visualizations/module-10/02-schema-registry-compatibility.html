Schema Registry: schema evolution and compatibility

The business wants a roaming flag and a network field on every voice CDR, and billing-svc can't stop while you add them. Schema Registry stops a breaking change before it reaches Kafka: the producer asks the registry first, and an incompatible schema gets 409. Pick a compatibility mode, apply one change to CdrVoice, press Check, then Register. Find a change that passes BACKWARD but fails BACKWARD_TRANSITIVE.

The compatibility modes

ModeThe registry checksSafe changes (Avro)Upgrade first
BACKWARD (default)A reader on the new schema can read data written with the latest oneAdd a field with a default; remove a field; widen int → longConsumers
FORWARDA reader on the latest schema can read data written with the new oneAdd any field; remove a field that had a defaultProducers
FULLBoth directionsAdd or remove fields that have defaultsEither, in any order
…_TRANSITIVEThe same, against every earlier version, not just the latestAs above, for the whole historyNeeded when old data stays on the topic (long retention, replays, compacted topics)
NONENothingAnything, including breaking changesCoordinate by hand, or write to a new topic

What the registry stores

A subject (by default <topic>-value and <topic>-key) holds versions 1, 2, 3 … Each version has a registry-wide schema ID. Every record carries a magic byte 0, the 4-byte ID and then the Avro bytes, so a consumer fetches the schema by ID and can decode any version on the topic.

Cloud and Platform

Cloud: one Schema Registry per environment, reached with a separate Schema Registry API key. Platform lab: cp-services.lab.internal:8081 with your LDAP user, and RBAC ResourceOwner on subjects starting with lNN.. Both start with {"compatibilityLevel":"BACKWARD"}.

Admin gotcha: Kafka brokers don't read your records. In Apache Kafka nothing stops a producer that skips the registry. Confluent Platform can check on the broker as well: set confluent.value.schema.validation=true on the topic, and the broker rejects records without a valid schema ID. In production, also set auto.register.schemas=false on producers and register schemas from CI.
Production trap: switching a subject to NONE "just for this release" lets a breaking schema through. Every consumer still on the old schema then fails on the next record, and the bad records stay on the topic until retention removes them. Use a new field with a default, or a new topic.
