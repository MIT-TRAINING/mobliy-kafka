Delivery semantics: at-most-once, at-least-once, exactly-once

Delivery semantics come from where you commit the offset relative to the work. A rating service reads CDRs from cdr.voice and writes one charge per call to billing.charges. Pick a mode, crash the service on the third CDR, and see which subscribers get missed or billed twice.

The three contracts

SemanticsOrder of operationsOn crashTelecom fit
At-most-oncecommit offset → processRecords in flight are lostNetwork telemetry samples, dashboards
At-least-onceprocess → commit offsetRecords in flight are reprocessed (duplicates)Most pipelines, if the consumer is idempotent (dedupe on CDR ID)
Exactly-onceread → produce + offsets in one transaction → commitOpen transaction aborted; readers never see itBilling, balances, fraud counters: Kafka-to-Kafka processing
Exactly-once building blocks: an idempotent producer with a stable transactional.id (initTransactions() fences off zombie instances), sendOffsetsToTransaction(offsets, consumer.groupMetadata()) so the input offsets commit in the same transaction as the output, and isolation.level=read_committed on every downstream consumer. Kafka Streams wraps all of this as processing.guarantee=exactly_once_v2.
Production trap: the default consumer isolation.level is read_uncommitted. A billing reader left on the default does see aborted transactional records. Switch the reader in the simulation and watch a subscriber get double-billed even in exactly-once mode. Also, exactly-once stops at Kafka's edge: writes to an external database or SMS gateway need their own idempotency key.
