Confluent Cloud vs self-managed Confluent Platform

Choosing a deployment model means choosing which layers you are paged for. Switch between the four models and watch ownership of each layer move from your team to Confluent. Then fire an incident and see whose pager it goes to. Notice that two incidents go to you in every model.

What changes for an administrator

AspectSelf-managed (Apache or CP)Confluent Cloud
Broker accessSSH, server.properties, JMX, logsNone. There are no broker hosts or broker configs to change
Install and upgradecp-ansible, CFK, packages or tarballs. You run the rolling upgrade (Module 5, Topic 3)Confluent upgrades the cluster for you with rolling restarts
Topic settingsAny topic config, any replication factorReplication factor is always 3. You can edit a documented subset of topic configs (for example retention.ms, cleanup.policy, max.message.bytes)
AuthenticationSASL/SCRAM, mTLS, LDAP via MDS (Module 7)API keys (SASL/PLAIN over TLS) or OAuth, tied to a user or service account
MonitoringJMX → Prometheus / Grafana, Control CenterCloud Console and the Metrics API (Module 8)
ScalingAdd brokers, then reassign partitions or let Self-Balancing do itBasic, Standard and Enterprise scale elastically within limits. On Dedicated, you choose the number of CKUs
CostHardware + people + licencePay per use: throughput, storage, partitions, cluster type
Confluent Cloud cluster typeTypical use
BasicDevelopment and test. Multi-tenant, lowest cost. Your lab environment env-lNN uses one
StandardProduction on a shared, multi-tenant cluster with a higher uptime SLA
EnterpriseProduction with private networking, scaling elastically
DedicatedSingle-tenant capacity sized in CKUs. Private networking, highest limits
FreightVery high-throughput workloads such as logging, which can accept higher latency
Admin takeaway: moving to Cloud takes infrastructure work off your plate, not Kafka work. Consumer lag, poison messages, permissions, topic design and client configs (acks, retries, idempotence) are still yours in every model. Plan your on-call rota around them.
Admin gotcha: a script that runs kafka-configs.sh --entity-type brokers or kafka-reassign-partitions.sh works on your self-managed cluster but fails on Confluent Cloud, where you can't change broker configs or move partitions. Audit your runbooks before you migrate: every broker-level step needs a Cloud equivalent, or it has to go.
