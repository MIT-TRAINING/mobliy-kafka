Adding & removing brokers with kafka-reassign-partitions.sh

A new broker joins the cluster empty. Kafka never moves existing partitions for you. To use the new broker, or to empty an old one before removing it, you plan a move with --generate, start it with --execute, and confirm it with --verify. Run the three steps for l07.cdr.voice on the shared cluster. Then try it without rack awareness and without a throttle, and see what each one costs you.

Adding vs removing a broker

Scale out

  1. 1Start the new broker with a new node.id and its broker.rack. It registers with the KRaft controllers and gets no partitions.
  2. 2Generate a plan that includes the new broker in --broker-list. Execute it with a throttle.
  3. 3Verify until every partition is complete, then run a preferred leader election so the new broker also takes some leader traffic.

Scale in

  1. 1Generate a plan whose --broker-list leaves the old broker out, and execute it.
  2. 2Verify, then check that kafka-topics.sh --describe no longer shows the broker in any replica list. Check internal topics like __consumer_offsets too.
  3. 3Stop it, then remove its registration: kafka-cluster.sh unregister --bootstrap-server $BS --id 13.
Admin gotcha: brokers 11 and 14 share rack ap-south-1a, so the rack-aware plan can't balance the load. With RF 3 and three racks, every partition needs one replica in each rack, and racks 1b and 1c have one broker each. Brokers 12 and 13 therefore end up with every partition. To balance, add brokers in matching numbers per AZ.
Production trap: --generate starts from a random broker and doesn't try to move as little data as possible. On a large cluster it can move far more than it needs to. Check the plan, or edit it by hand, before you execute. Always pass --throttle, and always finish with --verify. Otherwise the throttle stays set and will slow down the next broker that has to catch up after a restart.
