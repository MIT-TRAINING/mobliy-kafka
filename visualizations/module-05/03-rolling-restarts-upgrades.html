Rolling restarts & upgrade considerations

A rolling restart takes one node down at a time, so the cluster never stops serving. It only works if each broker is back in the ISR before you stop the next one. Roll the shared cluster's 4 brokers with the health check, then with a fixed sleep 30, and compare how long partitions refuse acks=all writes. Then switch to Upgrade, move every node from 4.2 to 4.3, and finalize the feature level.

Rolling restart checklist

StepCommand / checkWhy
1 · Check health firstkafka-topics.sh --bootstrap-server $BS --describe --under-replicated-partitions (and --under-min-isr-partitions) must print nothingIf a partition is already missing a replica, stopping one more broker can take it below min.insync.replicas
2 · Check the quorumkafka-metadata-quorum.sh --bootstrap-server $BS describe --status: all voters present, and a low MaxFollowerLagYou need a working controller quorum to move leaders and fence brokers
3 · Stop cleanlysudo systemctl stop kafka sends SIGTERM, which starts a controlled shutdownLeadership moves to other brokers before the process exits, and the logs are flushed, so restart is fast
4 · Change and startEdit server.properties or swap the binaries, then sudo systemctl start kafkaKeep node.id, log.dirs and meta.properties the same
5 · Wait for catch-upRepeat step 1 until it prints nothingThe broker is only back in the ISR once its replicas have caught up
6 · Afterwardskafka-leader-election.sh --election-type preferred --all-topic-partitionsThe last broker you restarted leads nothing until leaders are rebalanced

Upgrading Kafka 4.x

Two phases

  1. 1Roll the binaries on every controller and broker, one at a time, with the checklist above. The cluster keeps running at the old feature level (metadata.version), so you can still roll back to the old binaries.
  2. 2Finalize once every node runs the new version and you've watched it run normally: kafka-features.sh --bootstrap-server $BS upgrade --release-version 4.3. From then on, new metadata features are switched on and rolling back the binaries is no longer supported.

Before you start

From 3.x on ZooKeeper
4.x has no ZooKeeper mode. Migrate to KRaft on 3.9 first, then upgrade (Module 1, Topic 6).
Java
Kafka 4.x brokers and tools need Java 17 or later. Clients can still run on Java 11.
Release notes
Check for removed configs and changed defaults before you roll. A broker that won't start halfway through a roll leaves a partition under-replicated.
Current level
kafka-features.sh --bootstrap-server $BS describe shows the finalized metadata.version.
Admin gotcha: a restart script with a fixed sleep 30 works on a quiet test cluster. It fails in production, where a broker that was down for 2 minutes has gigabytes of CDRs to catch up on. Make the script wait until --under-replicated-partitions prints nothing, with a timeout that stops the roll.
Admin takeaway: kill -9 skips the controlled shutdown. Partitions led by that broker have no leader until the controller fences it (broker.session.timeout.ms, 9 s). When it restarts, it first has to run log recovery. Use kill -9 only for a broker that is already hung.
