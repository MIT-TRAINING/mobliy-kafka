Topic 4

Cluster architecture: brokers, replicas & offsets

A 3-broker cluster hosts topic payments with 3 partitions. Each partition is copied to replication factor brokers: one leader handles reads and writes, followers fetch from it. Produce data, kill a broker, and watch leader election, ISR shrink/expand and the high watermark.

Key terms

Cluster
A set of brokers working together; one acts as the controller managing leadership and metadata.
Replication factor
How many copies of each partition exist. RF=3 tolerates 2 broker failures for reads (with suitable min.insync.replicas).
Leader / follower
Clients produce to and (by default) consume from the leader. Followers continuously fetch to stay in sync.
ISR
In-Sync Replicas — replicas caught up with the leader (within replica.lag.time.max.ms). Only ISR members can become leader when unclean election is disabled.
LEO
Log End Offset — the offset of the next record to be written on a given replica.
High watermark
Highest offset replicated to all ISR members. Consumers can only read below it, so they never see data that could be lost on failover.
Consumer lag
How far a consumer group is behind: log-end offset − committed offset. The #1 metric admins watch.
Try this: set RF=1, produce, then kill broker-1. Partition P0 goes offline — no other copy exists. With RF=3, the same failure causes only a brief leader election. Also note records above the high watermark on a dead leader can be truncated: that's why producers use acks=all (covered in Module 3).
