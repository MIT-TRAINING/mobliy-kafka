Topic 1

Messaging models: queue vs. pub-sub vs. Kafka's log

If you know IBM MQ, you already know two delivery models. Kafka adds a third: a durable, replayable log where reading a message doesn't remove it. Switch modes below, send messages, and click a consumer to take it offline.

Tip: click a consumer to toggle it offline

Queue — competing consumers

Each message is delivered to exactly one consumer and is removed once acknowledged. Adding consumers spreads the load (like multiple applications reading from one IBM MQ local queue). Take all consumers offline and watch the queue depth grow — messages wait, but once consumed they're gone for good.

Classic pub-sub — every subscriber gets a copy

The broker fans each message out to every active subscriber. With a non-durable subscription, a subscriber that is offline when the message is published misses it. (IBM MQ durable subscriptions fix this by keeping a per-subscriber queue, at the cost of storing a copy per subscriber.)

Kafka — an append-only log with consumer offsets

Messages are appended to a log and stay there until retention removes them. Each consumer group keeps its own offset (a bookmark). One stored copy serves any number of groups. Take audit-svc offline: its lag grows, and when it comes back it catches up from where it left off. Hit Rewind to replay history — impossible in a classic queue.

How Kafka compares with IBM MQ and traditional messaging

AspectIBM MQ / traditional brokerApache Kafka
Core abstractionQueues and topics; broker tracks delivery per messagePartitioned, append-only log; consumers track their own offsets
After consumptionMessage is removed (destructive get)Message stays until retention time/size or compaction removes it
ReplayNot possible once consumed (unless re-sent)Reset offsets and re-read any retained data
Fan-outCopy per subscriber / per queueOne stored copy; many consumer groups read independently
OrderingPer queue (weakened with competing consumers)Strict per partition; related records share a key → same partition
ScalingQueue managers, clusters, shared queuesAdd partitions and brokers; consumers scale up to the partition count
TransactionsXA / two-phase commit, per-message ackIdempotent producer + transactions (exactly-once within Kafka)
Sweet spotRequest/reply, command messaging, strict per-message workflowHigh-throughput event streams, integration backbone, stream processing
Kafka can behave like both models: consumers in the same group share partitions (queue semantics), while different groups each receive every message (pub-sub semantics). You'll see this in Topic 3.
