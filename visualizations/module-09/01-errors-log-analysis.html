Common Confluent Cloud and Platform errors, and how to read the logs

Every Kafka request passes the same stages: your code, the connection, authentication, authorization, metadata, the partition leader and the response. An exception tells you which stage refused it, and whether retrying can ever help. Pick a symptom, then switch between the client log, the broker log and the metrics. Then switch to Confluent Cloud and see which evidence you lose when Confluent runs the brokers.

Client log

Always yours, on both Platform and Cloud. Find the first ERROR or WARN and its exception class. The 500 lines after it are usually consequences.

Broker log

Platform only. On the lab brokers it is /var/log/kafka/server.log, readable by the trainer over SSM. Look for Shrinking ISR, Failed authentication and ERROR lines in the same minute as the client error.

Metrics

They show the problems that log nothing, such as throttling and lag. Platform: JMX and Control Center. Cloud: the Metrics API (client_limit_milliseconds, consumer_lag_offsets) and the Console.

Admin gotcha: a producer that gets a retriable error keeps retrying silently until delivery.timeout.ms (2 minutes by default). You see a WARN … retrying line, not an error, so search client logs for WARN as well as ERROR.
Production trap: on Confluent Cloud there is no server.log to read. Before an incident, make sure every application logs Kafka client WARNs with timestamps in UTC and records its client ID. Then the client log and the Metrics API are enough for you and for Confluent Support (Topic 5).
