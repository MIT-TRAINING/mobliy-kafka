Consumer lag analysis and remediation in Confluent

Lag is a symptom with several causes, and each cause has its own fix. Adding consumers cures one of them and does nothing for the rest. l09.billing reads l09.cdr.voice. Press Run, then cause trouble with the checkboxes. Read the shape of the lag: does it grow everywhere or on one partition, steadily or in a saw-tooth? Then fix it.

Read the shape, then pick the fix

What the lag looks likeCauseFixNot the fix
Grows on every partition, steadilyTotal consumer capacity is below the produce rateMore consumers (up to the partition count), or faster processingRestarting the group
Some consumers have no partitionsMore consumers than partitionsMore partitions (plan for key ordering), or fewer consumersAdding even more consumers
One partition grows, the others are near 0Hot key: one partition gets more than one consumer can processBetter key design, faster processingMore consumers: one partition is only ever read by one member of the group
One partition frozen at a single offset, errors in the logPoison record (RecordDeserializationException)Dead-letter topic and skip, then fix the producerResetting offsets to latest: that skips good CDRs too
Saw-tooth: drains, jumps, members come and goA poll batch takes longer than max.poll.interval.ms, so the member is removed and its work redoneLower max.poll.records; speed up the slow callRaising session.timeout.ms: heartbeats are fine

Platform lab

Control Center's consumer lag pages (the brokers emit lag), or kafka-consumer-groups.sh --bootstrap-server $CP --command-config $CFG --describe --group l09.billing. The LAG column is log-end offset minus committed offset per partition.

Confluent Cloud

The Metrics API metric consumer_lag_offsets, grouped by metric.consumer_group_id and partition, about 3 minutes behind. Or the Console's consumer group page. kafka-consumer-groups.sh works against Cloud too, with an API key.

Admin takeaway: lag in records doesn't tell you whether you're in trouble. Divide it by the drain rate: 120,000 records at +2,000/s is a minute behind, while 5,000 records that keep growing is an incident. Alert on lag that keeps growing (Module 8, Topic 1), not on a fixed number.
Production trap: lag turns into message loss when it grows past retention. If l09.billing is 3 days behind and retention.ms is 1 day, the oldest CDRs are deleted before billing reads them, and the consumer jumps ahead under auto.offset.reset with only a log line. Topic 6 drills this.
