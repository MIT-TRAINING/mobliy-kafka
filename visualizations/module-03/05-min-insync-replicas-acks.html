Topic 5

min.insync.replicas & acknowledgments (acks)

Durability is a contract with two sides: the producer's acks decides when a write counts as successful; the broker's min.insync.replicas decides whether an acks=all write is accepted at all. Produce, kill brokers, and watch exactly which records can be lost.

Producer acks
Topic min.insync.replicas
RF=3 · acks=all · min.insync.replicas=2 → tolerates 1 failure
Three rules extracted from this simulation: (1) acks=all is only as strong as min.insync.replicas — with the default of 1 it can be acknowledged by a single replica ("last replica standing"). (2) min.insync.replicas does nothing for acks=0 or acks=1 writes — the broker only consults it for acks=all. (3) unclean.leader.election.enable=true trades correctness for availability: an out-of-sync replica can become leader and silently lose acknowledged data.

Kafka 4.x behaviour worth writing down: under the strict min-ISR rule (KIP-966) the high watermark stops advancing when the ISR drops below min.insync.replicas. Even acks=0/1 records written during that window are not visible to consumers until replication recovers — and would be lost if an out-of-sync replica were promoted. Newer 4.x releases also track Eligible Leader Replicas (ELR) so elections avoid that corner case.

Production baseline: RF=3, min.insync.replicas=2 on the topic, acks=all, idempotence on (enable.idempotence=true, the client default since Kafka 3.0 — as is acks=all). Older console-producer examples still assume acks=1, so when testing durability set --producer-property acks=... explicitly so you know which contract you are demonstrating.
