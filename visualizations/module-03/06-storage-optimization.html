Topic 6

Storage optimization techniques

Optimization without measurement is guessing. Start with the calculator: pick a codec, retention window and tiered-storage setting for a telecom CDR workload and see the broker disk requirement change live. Then use the symptom explorer to practise the diagnostic sequence admins actually run.

1 · Size the cluster before it fills

Recompression trap: never set a topic's compression.type to a codec unless you mean it. compression.type=gzip at topic level tells brokers to decompress and recompress every batch that arrives with a different codec — a large CPU tax on the data path. Compress in the producer (or match a cluster-wide dynamic default to the producer codec); leave the topic at producer.

SituationSegment recommendation
High-volume topics (CDRs, telemetry)Keep the 1 GiB default — fewer files, efficient I/O
Low-volume topics with tight retentionLower segment.ms and/or segment.bytes (128–256 MiB) so rolls happen
Compacted topicsModerate segment.ms (hours) — the cleaner only touches sealed segments
Very short-lived dev/test topicsSmall is fine in dev — never in production (file-handle explosion)
Tiered storage separates how long data must exist from how much sits on broker disks: sealed segments are uploaded to object storage, and only a small local window survives (local.retention.ms / local.retention.bytes), while retention.ms governs the remote copy. Apache's KIP-405 implementation has been production-ready since 3.9; Confluent ships its own (confluent.tier.*) which is not the same feature and does not support JBOD.
