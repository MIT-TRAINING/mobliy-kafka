Topic-level configuration overrides with kafka-configs.sh

One cluster, many kinds of data: cdr.voice needs days, subscriber.plan needs the latest value per key forever, audit.events needs 30 days. Build a real kafka-configs.sh command below — including the broker-name trap — and read the synonyms that prove which layer won.

Run a command to see CLI output here.

Effective configuration per topic

Overrides shown as pills; unset keys fall through to the broker default.

Exact-name trap: topic-level properties never carry the log. prefix. log.retention.ms exists only at broker level; passing it with --entity-type topics fails with an InvalidConfigurationException. Worse: a typo can look accepted, so always confirm with --describe that the value actually landed.

KRaft propagation: a topic override is appended to the __cluster_metadata log by the active controller and fetched by every broker — the same value everywhere, with no broker restart and no rolling restart (compare Module 1, Topic 6).
