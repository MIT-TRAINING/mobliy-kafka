Broker configuration parameters: defaults, static & dynamic layers

One property — retention.ms on cdr.voice — can be set at five different layers. Toggle the layers below and watch the effective value resolve differently on broker 1 and broker 2. The trap this page exists to teach: a per-broker override applies to the partitions that broker leads, not to the whole topic.

Highest priority wins: topic → per-broker → cluster-wide → static → built-in. The built-in default can never be unset.

Admin trap: set a dynamic config per broker and the same topic behaves differently depending on which broker leads each partition. Use --entity-default for cluster-wide intentions and reserve --entity-name N for genuinely node-specific resources such as num.io.threads. Always confirm with kafka-configs.sh --describe — the synonyms tell you which layer actually won.

Static vs. dynamic — what can change without a restart?

PropertyStatic (server.properties, restart)Dynamic (no restart)
log.dirs✓ — topology/identity settings are static—
node.id, process.roles✓—
controller.quorum.voters✓—
log.retention.ms / log.retention.bytes✓ (can also be set here)✓ — most common dynamic change
log.segment.bytes / log.roll.ms✓✓
min.insync.replicas✓✓
num.io.threads, num.network.threads✓✓ — node-specific by nature
In KRaft, a dynamic config change is appended to the __cluster_metadata log by the active controller; brokers pull the new record and update their cache — no restart and no ZooKeeper (Module 1, Topic 6). Static changes are applied with a rolling restart and ISR watching (Module 5).
