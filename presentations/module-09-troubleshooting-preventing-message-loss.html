The model · where a message can go missing

A CDR can only vanish at one of three hops

① Produce

The producer decides acks, retries and how long to try. A send that finally fails is the application's problem.

② Store

The broker keeps the record on RF replicas. min.insync.replicas decides how many must have it before the ack.

③ Consume

The consumer decides when to commit. Commit before the work is done, and a crash skips the record.

Lost or late?

Late is lag: the record is still in the log. Lost means it was never written, or deleted before anyone read it.

This is the same three-hop picture you saw for delivery semantics in Module 4, now used as an investigation map. Point at each falling CDR in turn: hop one is the producer giving up, hop two is a replica dying before the others copied the record, hop three is a commit that ran ahead of the work. The fourth card matters most in an incident: most "missing" CDRs are late, still in the log behind the consumer, and nothing is lost yet. Ask: in MQ terms, which hop is closest to a message sitting on the dead-letter queue?

Read an error in two steps. First, is it retriable? If it is, the client is already retrying for you and you mostly see WARN lines. The danger is the moment the retries run out, because that TimeoutException lands in the application's callback. Second, if it is not retriable, nothing will heal by waiting, so go straight to the key, the binding or the config. Point at the Hop column: every row maps back to one of the three hops. Topic 1 · Log analysis

Line up every log on one UTC timeline

# 1 · client log (your app, or the CLI's stderr), times in UTC [09:14:03,512] WARN [Producer clientId=l07-mediation] Got error produce response … on topic-partition l07.cdr.voice-1, retrying (…) Error: NOT_ENOUGH_REPLICAS [09:16:03,520] ERROR … TimeoutException: Expiring 312 record(s) for l07.cdr.voice-1: 120004 ms has passed since batch creation # 2 · broker log, Platform only (trainer, on cp-broker-2) $ sudo grep -E "ERROR|WARN" /var/log/kafka/server.log | grep l07.cdr.voice [09:14:03,498] ERROR [ReplicaManager broker=2] Error processing append operation on partition l07.cdr.voice-1 … NotEnoughReplicasException … $ sudo grep l07 /var/log/kafka/kafka-authorizer.log # denials # 3 · Cloud: no broker logs. Use client logs and the Metrics API. # log lines abridged with … for the slide
Logs from different machines only tell a story once they share a clock, so write every time in UTC and start from the first event, not the loudest one. Here the broker stopped first, the under-min-ISR metric moved with it, and the client's WARN lines started a moment later. The ERROR that the application team reported came two minutes after that, when delivery.timeout.ms ran out. On Confluent Platform the trainer can read /var/log/kafka on the brokers; on Cloud you never see a broker log, so your client logs and the Metrics API are the whole record. Ask: which timestamp would you have put in the incident ticket, 09:14 or 09:16?
Topic 2 · Root causes of message loss: acks and replication factor

acks=all with RF 3 and min ISR 2 survives losing a broker

Partition state (RF 3, min ISR 2)acks=all producersacks=1 producersWhat you do
Healthy · ISR 3 of 3Writes succeedWrites succeedNothing
Under-replicated · ISR 2 of 3Writes succeed, still safeWrites succeed, less marginFind the slow or dead broker
Under min ISR · ISR 1 of 3NotEnoughReplicasExceptionAppends, high watermark frozenPage someone now
This is the durability contract from Module 5, seen from the incident side. acks=0 and acks=1 do not fail loudly when they lose data: the producer was told "fine", so the loss only shows up later as a gap in billing. acks=all moves the failure to the front: under min ISR the producer gets NotEnoughReplicasException, which is noisy but loses nothing. On Cloud the replication factor is fixed at 3 and min.insync.replicas can be 1 or 2, so the producer's acks is the setting you must check; on the shared Platform cluster min.insync.replicas=2 is the cluster default. Keep unclean.leader.election.enable=false, because an unclean election picks a replica that lacks committed records. Ask: would you rather see an error at 09:14 or a billing gap at month end?
Topic 2 · Root causes of message loss: quota and throttling limits

Throttling only delays: giving up is what loses the CDR

LimitWhere it appliesHow you see it

Cluster-type limits: eCKUs and CKUsConfluent CloudMetrics API throttle time, as in Module 8
buffer.memory, the producer's own bufferEvery producersend() blocks, BufferExhaustedException
A quota never drops a record: the broker simply holds back its response so the client slows down. That is safe as long as the application keeps waiting. Loss starts at the red deadline: after delivery.timeout.ms the record fails in the callback, and an application that logs and carries on has just discarded a CDR. Point at the two outcome boxes: the fix for a throttling incident is in the application's error handling as much as in the quota. Ask: what does your mediation application do today when a send fails after two minutes?
Topic 3 · Troubleshooting connectivity

Climb the connection ladder one rung at a time

# 1 · DNS: the bootstrap name resolves (three brokers behind it) $ getent hosts cp-kafka.lab.internal # 2–3 · TCP and TLS: port open, chain trusted by the course CA $ openssl s_client -connect cp-kafka.lab.internal:9092 \ -CAfile $CP_CA </dev/null | grep "Verify return code" Verify return code: 0 (ok) # 4 · SASL: your LDAP user can log in at all $ confluent login --url $MDS_URL --certificate-authority-path $CP_CA # 5–6 · Kafka end to end: metadata lists every broker $ kafka-broker-api-versions.sh --bootstrap-server $CP \ --command-config $CFG | grep "(id:" # Cloud: same ladder, the API key replaces the LDAP login $ confluent api-key list --resource lkc-…
A connection fails at exactly one rung, and the error message usually names it, so start at the bottom and stop at the first rung that fails. The most common rung on our clusters is TLS: bootstrapping with an IP address instead of cp-kafka.lab.internal fails the certificate name check, exactly as the Module 7 troubleshooting table warned. The top rung is the sneaky one: the bootstrap works, but the broker then hands back advertised.listeners addresses that your network cannot reach, the trap from Module 2. Ask: which rung would a firewall change break, and what error would you expect?
Topic 3 · Troubleshooting client-side issues

Before you suspect the brokers, check the client: most consumer incidents are a loop that is too slow for its settings. Follow the timer bar: 500 records at one second each is 500 seconds, but the group only waits 300, so the member is thrown out, its commit fails and the next owner reprocesses the batch. That is a duplicate, not a loss, but the auto-commit row is a real loss: records handed to worker threads are committed before the threads finish. These are the Module 4 settings, now read as symptoms. Ask: which of these rows would show up as lag in Control Center, and which would not?
Topic 4 · Consumer lag analysis and remediation in Confluent

Lag rising? First ask: every partition, or just a few?

Turn lag into time

Lag ÷ consume rate = time behind. 48,000 CDRs at 400/s is 2 minutes: compare that with billing's deadline.

Watch the drain

Lag falls only while consume rate > produce rate. Time to zero = lag ÷ (consume − produce).

Skip a record only on purpose

Moving the offset past a poison pill is a decision to lose it. Dry-run first, and get the data owner's agreement.

Compare it with retention

Lag older than retention.ms is deleted before billing reads it. That is the next slide.

You built lag alerts in Module 8; this is what you do when one fires. The first question splits the problem in two: lag on every partition means capacity, lag on a few partitions means something specific to those partitions. A stuck offset on one partition is the classic poison pill from Module 4: one record the consumer cannot process blocks everything behind it. Adding consumers only helps up to the partition count, because each partition has one consumer in a group. Ask: if partition 1 alone climbs while its offset still moves, what would you look at in the producer?
Topic 4 · Remediation when lag outlives retention

Lag becomes loss when retention deletes unread CDRs

# where does billing stand? Compare CURRENT-OFFSET with the log start $ kafka-consumer-groups.sh --bootstrap-server $CP --command-config $CFG --describe --group $ME.billing # choose the restart point on purpose: billing stopped, dry-run first, then --execute $ kafka-consumer-groups.sh --bootstrap-server $CP --command-config $CFG --group $ME.billing \ --topic $ME.cdr.voice --reset-offsets --to-datetime 2026-10-12T09:00:00.000 --dry-run # critical consumers: auto.offset.reset=none fails loudly instead of skipping
Lag is harmless until it is older than the topic's retention. Follow the animation: retention deletes the oldest segment on schedule, whether or not billing has read it, and billing's committed offset now points at nothing. What happens next is decided by auto.offset.reset: the default latest silently skips everything that is still there, which turns a small loss into a big one. A second trap from Module 4 behaves the same way: a group that stays empty longer than offsets.retention.minutes, 7 days by default, loses its committed offsets. Ask: for a weekly batch consumer, which two settings would you change?
Topic 5 · Confluent support and escalation model

Who owns the failing layer decides who you call

Evidence for the caseWhy Support needs itWhere you get it
Cluster IDFinds your cluster among thousandslkc-… in the Console; Platform: kafka-cluster.sh cluster-id
Time window in UTCLines your evidence up with their logsThe first error, not the time of the ticket
Exact error and client versionSeparates a client problem from a broker problemThe log excerpt from your timeline
What changed, and the impactMost incidents follow a change; impact sets the severity"Billing short 312 CDRs since 09:14 after a key rotation"
The shared-responsibility split decides your first call. On Cloud the brokers are Confluent's layer, so a broker-side fault is a support case, but your keys, bindings and client settings are still yours to fix. On Platform you run everything, and Support helps you diagnose the software. Before you open a case, do the triage from today and check the status page, because a good case with a precise UTC window and an exact error is answered much faster. Severity follows business impact: production down or data being lost now is the top severity. Confirm the response times of your own support plan before you need them. Ask: who in your organisation is allowed to open a top-severity case?
Topic 6 · Best-practice checklist for preventing message loss

Close every hop: a checklist you can audit

① Producer

acks=all and enable.idempotence=true. A delivery.timeout.ms you chose. Real code for a failed callback, never "log and continue".

② Topic & broker

RF 3, min.insync.replicas=2, unclean.leader.election.enable=false, replicas on three racks, retention longer than your longest outage.

③ Consumer

Commit after processing. Choose auto.offset.reset on purpose. Size max.poll.interval.ms for the batch. Send poison pills to a dead-letter topic.

④ Operations

Alert on lag, under-min-ISR and offline partitions, and throttle time. Rehearse a broker loss. Rotate keys and certificates before they expire.

This checklist sums up the whole module: one column per hop, plus the operations that watch them all. Use it as an audit: for each production topic, ask the owning team to show you each line in their config or their code. The producer column is where most real losses start, because acks and the callback live in application code that the platform team never sees. Ask: which line of this checklist would fail first if you audited your busiest MQ-to-Kafka flow today?

Wrap-up

Key takeaways, and a quick self-check

01Three hops

Produce, store, consume. Find the hop first, then the cause. Late is not lost.

02Errors name the layer

Retriable errors heal until delivery.timeout.ms; fatal ones need a fix to the key, binding or config.

03acks=all, RF 3, min ISR 2

Survives one broker loss. acks=1 can lose a CDR it has already acknowledged.

04Throttling delays

The loss happens when the application gives up on a failed send and carries on.

05Lag vs retention

Lag older than retention is deleted unread. Reset offsets on purpose, never by default.

06Escalate with evidence

Cluster ID, UTC window, exact error, what changed and the impact.
