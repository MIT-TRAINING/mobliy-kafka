Topic 1 · Broker configuration parameters

Five layers, and the top one wins

!
MQ admins: a per-broker dynamic config can make the same topic behave differently depending on which broker leads the partition. Set cluster-wide defaults with --entity-default. Keep per-broker settings for node resources such as num.io.threads.
Read the synonyms in kafka-configs.sh --describe before you change anything. The label tells you which layer won: topic, this broker, the cluster default, server.properties, or the built-in. A topic override beats all of them and does not need a restart. Ask: if two brokers disagree, which command shows you that?

Topic 2 · Log directories and segment management

One directory per partition, three files per segment

.log — record batches. The file name is the segment's base offset.

.index — sparse offset-to-byte map, so a fetch does not scan the file.

.timeindex — sparse timestamp-to-offset map, used by time retention.

JBOD — a failed disk offlines only its partitions. The broker keeps serving the rest.

Everything for a partition lives in one directory named topic-partition. The active segment's index is pre-allocated to 10 MiB and trimmed when the segment closes — a 10 MB index on a small active segment is normal. Kafka does not rebalance partitions between disks, so choose log.dirs at install time. Ask: if /data/d2 dies, which partitions are affected?
Topic 2 · Log directories and segment management

Retention never touches the active segment

Size. Rolls at segment.bytes, default 1 GiB.

Age. Rolls at segment.ms, default 7 days.

Index full. Rolls when the index hits 10 MiB.

Quiet-topic trap. A 1-day retention still keeps old data until the active segment rolls.

Only the newest segment accepts appends. The moment it rolls, retention and compaction are allowed to look at it — not before. That is why "retention is one day but I still see last month" is almost always a segment that has not closed. Lower segment.ms on low-traffic topics when deletion precision matters. Ask: what has to happen before a record can be deleted?
Topic 3 · Topic-level configuration overrides

Change retention without a restart

# topic names have no log. prefix $ kafka-configs.sh --bootstrap-server $BS --alter \ --entity-type topics --entity-name cdr.voice \ --add-config retention.ms=86400000 $ kafka-configs.sh --bootstrap-server $BS --describe \ --entity-type topics --entity-name cdr.voice retention.ms=86400000 synonyms={DYNAMIC_TOPIC_CONFIG:retention.ms=86400000, DEFAULT_CONFIG:retention.ms=604800000} $ kafka-configs.sh … --add-config log.retention.ms=86400000 InvalidConfigException
There is no ZooKeeper and no broker restart. The alter becomes a metadata record, every broker fetches it, and the next produce uses the new value. --delete-config removes only the override; the value falls back down the chain. Always describe afterwards and read the synonym. Ask: why did the broker name fail on a topic?
Topic 4 · Retention policies (time-based and size-based)

Time or size: whichever breaches first

RuleWhat it means on the broker
AgeThe newest record in the segment, not the oldest. One fresh record keeps the whole file.
UnitWhole closed segments. retention.ms is not a per-message TTL.
Both limitsWhen time and size are set, the first one breached deletes. Size is per partition: 6 × 10 GiB = 60 GiB.
CadenceChecked every 5 min. Files are renamed *.deleted, then removed after 60 s.
Retention does not wait for consumers. A billing job that is down longer than retention.ms misses data for good — that shows up again in Module 9. With the default CreateTime, a producer timestamp is what ages the segment; replaying old timestamps can make data eligible immediately. Ask: a topic has 6 partitions and retention.bytes of 10 GiB. What is the worst case on one broker if it leads all six?
Topic 4 · Cleanup policies: delete vs. compact

Events stay a history. State becomes a table.

delete · cdr.voice Every call record in the window matters. Keys are optional.

compact · subscriber.plan Only the latest plan per MSISDN. Keyless records pile up forever.

compact,delete · tariff.changes Latest per key, then the key itself expires with retention.ms.

Compaction keeps the latest record per key and leaves offset gaps, so consumers do not see a rewritten history. A null value is a tombstone and stays visible for delete.retention.ms, 24 hours by default, so a lagging consumer still learns the key was removed. The cleaner is lazy: set max.compaction.lag.ms when old values must disappear by a deadline. Ask: what happens to a compacted topic if the producer sends no key?
Topic 5 · min.insync.replicas and acknowledgments (acks)

acks=all is only as strong as the ISR floor

ISRacks=allacks=1What can be lost

The table assumes replication factor 3 and min.insync.replicas 2 — the production baseline, with idempotence on. The broker default of min.insync.replicas is 1, so acks=all can be acknowledged by a single copy. min ISR does nothing for acks=0 or acks=1. The Java producer defaults to acks=all since Kafka 3.0; set the console producer explicitly. Ask: who is lying if the topic says min ISR 2 and the producer uses acks=1?
Topic 5 · min.insync.replicas and acknowledgments (acks)

When the ISR shrinks, the high watermark freezes

Pair them. acks=all with the default min ISR of 1 is a single copy.

acks=1 bypasses the floor. min ISR is consulted only for acks=all.

No unclean election. Leave unclean.leader.election.enable false.

Kafka 4.x holds the high watermark while the ISR is below min.insync.replicas, so consumers do not read the acks=1 record until replication recovers. You will raise the floor with the broker still down, instead of stopping two nodes — on a laptop cluster that would also break the controller quorum. You may see an Elr column in describe on 4.x. Ask: why is the record the producer "sent" missing from the consumer?
Topic 6 · Storage optimization techniques

What actually shrinks the log

Producer codec

zstd for most topics, lz4 when latency matters. Leave the topic at compression.type=producer.

Topic codec

compression.type=gzip makes the broker recompress every batch that arrives in another codec. That is a CPU tax.

Segment size

Busy topics such as cdr.voice keep the 1 GiB default. Quiet topics lower segment.ms so retention can run.

Batches

Compression works on the whole batch. linger.ms and batch.size are the Module 4 knobs that make it pay.

On JSON CDRs, producer-side zstd or lz4 is often 40 to 80 percent less disk and replication traffic. gzip still compresses well and is rarely worth the CPU. Thousands of tiny segment files means the roll settings are too aggressive; one huge active segment means retention cannot act. Ask: where should the codec be set if you do not want the broker to recompress?
Topic 6 · Storage optimization techniques

Keep a hot window on the broker

kafka-log-dirs.sh

Size of every partition. Pipe the JSON to jq. This is the first command when a disk alert fires.

kafka-configs.sh --describe

The retention and cleanup you intended, and which layer actually won.

local.retention.ms

How long the copy stays on broker disk after it has been uploaded. Example: 1 day.

retention.ms

How long the remote copy lives. Example: 365 days for an archive topic. Opt in with remote.storage.enable=true.

Apache tiered storage is KIP-405, on by remote.log.storage.system.enable at the broker. Confluent Tiered Storage is a different feature, confluent.tier.*, and it does not support JBOD — that arrives with Module 6. Measure before you tune: log dirs for size, configs for intent, then ls the partition directory. Ask: a 70 percent disk that grows 5 percent a day — is that healthier than a flat 90 percent?
Hands-on · Retention, replication and durability

Design the topic, then prove the contract

# 01 · shared AWS cluster — do not stop these brokers # $APACHE = apache-kafka.lab.internal:9092 $CFG = ~/kafka/apache.properties $ kafka-topics.sh --bootstrap-server $APACHE --command-config $CFG \ --create --topic $ME.cdr.voice --partitions 6 --replication-factor 3 \ --config retention.ms=604800000 --config segment.bytes=268435456 \ --config min.insync.replicas=2 --config cleanup.policy=delete $ kafka-configs.sh --bootstrap-server $APACHE --command-config $CFG \ --alter --entity-type topics --entity-name $ME.cdr.voice \ --add-config retention.ms=86400000 # 02 · local labs/module-02 — you may stop one broker $ docker compose stop kafka-2 # ISR = 2, acks=all still accepted $ kafka-configs.sh --bootstrap-server $BS --alter --entity-type topics \ --entity-name $ME.durability.test --add-config min.insync.replicas=3 $ … --producer-property acks=all # NOT_ENOUGH_REPLICAS $ … --producer-property acks=1 # accepted, hidden until the ISR recovers
01

Retention and replication

On the shared AWS cluster, create $ME.cdr.voice with a 7-day retention, RF 3 and min ISR 2, then shorten retention live.

02

Durability under acks

On your Module 2 cluster, stop one broker, raise min ISR to 3, and compare acks=all with acks=1.

labs/module-03 is not in the repo yet — these commands are the guide's hands-on, the runtime companion. On AWS you use your learner prefix and apache.properties; SASL means --command-config. You cannot kill a shared broker. The failure half runs in labs/module-02, where $BS is the three-node internal listener. After the drill, set min ISR back to 2 and start kafka-2. Ask: why do we raise min ISR instead of stopping a second broker?
Wrap-up

Key takeaways, and a quick self-check

01Read the synonyms

Topic, broker, cluster default, file, or built-in. The label says which layer won.

02Static versus live

log.dirs and identity need a restart. Retention, segments and min ISR do not.

03The active segment stays

Retention and compaction only see closed segments. That is the quiet-topic trap.

04Per partition, first breach

retention.bytes is not a topic cap. Time or size — whichever trips first.

05The durability triple

RF 3, min.insync.replicas=2, acks=all. Either half alone is a false sense of safety.

06Shrink it on purpose

Compress on the producer. Retention never waits for a consumer.
