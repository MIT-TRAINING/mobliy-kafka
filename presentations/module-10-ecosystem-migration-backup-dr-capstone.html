A connector is a ready-made Kafka client: a source connector reads an outside system and produces, a sink connector consumes and writes to an outside system, and tasks do the actual copying. Topic 2 · Confluent Schema Registry: the contract

The schema travels once; every record carries only its ID

Subject

Where versions live. Default name <topic>-value, so on Platform your lNN. prefix also covers your subjects in RBAC.

Schema ID

A magic byte and a 4-byte ID before each payload. Both sides cache it: one registry call per schema, not per record.

Compatibility

A rule per subject. The registry default is BACKWARD: sr /config answers {"compatibilityLevel":"BACKWARD"}.

Its own access

Cloud: the registry lsrc-… needs its own API key. Platform: your LDAP user and the course CA.

In MQ the message format is an agreement in a document; here it is enforced by a service. Point at the dot that goes up to the registry only once: after that every record carries just five extra bytes, and the consumer looks the schema up by ID and caches it. Remind the room of Module 6 Lab 06: the most common Cloud mistake is to use the Kafka API key for the registry and get 401. Ask: what happens in your MQ flows today when a sender adds a field the receiver does not expect?
Topic 2 · Schema evolution and compatibility

The compatibility mode decides which side deploys first

ModeWhat it guaranteesDeploy firstSafe changes
BACKWARD (default)The new schema can read data written with the old oneConsumersAdd a field with a default · delete a field
FORWARDThe old schema can read data written with the new oneProducersAdd a field · delete a field that has a default
FULLBoth directionsEither sideAdd or delete only fields that have defaults
NONENo check at allEveryone at onceAnything, and anything can break
Walk the three versions from Module 6 Lab 06: v2 adds roaming with a default and is accepted, v3 adds network without one and is refused with 409 before a single record is written. That refusal is the registry protecting every consumer. Each mode also has a TRANSITIVE variant that checks every earlier version, not only the latest, which matters when consumers replay old data. Ask: under BACKWARD, if the producer team ships v2 before the consumers, what can break?
Topic 3 · ksqlDB on Confluent: overview

ksqlDB is SQL that runs as a Kafka application

QueryStatementWhere it runs, and for how long
PushSELECT … EMIT CHANGES;Streams new rows to your terminal until you stop it
PullSELECT * FROM … WHERE caller = '…';One answer from a table, then it ends, like a database
PersistentCREATE STREAM | TABLE … AS SELECT …On the server, forever, writing a new topic. Clean up with SHOW QUERIES, TERMINATE, DROP
A stream and a table are both views over a topic; the difference is whether you keep every event or only the latest value per key. Point at the persistent queries: they keep running on the ksqlDB server after you close your terminal, they create topics, and an aggregation keeps a state store with a changelog topic behind it. For an operator that means memory, disk and extra topics to watch, which is why the capstone allows one persistent query at a time. Ask: which consumer in TelcoPulse could a ksqlDB query replace, and which should stay a Java application?
Topic 4 · Backup and DR: what replication does not cover

Replication inside one cluster is not a backup

RF 3 protects

Against a broker or disk failure inside one site, as you proved in Module 5.

RF 3 does not

A deleted topic, bad data, a lost site: the replicas copy the mistake or go down together.

RPO

How much data you can lose: the replication lag at the moment of failure. Capstone target: 5 minutes.

RTO

How long until billing runs again: from the decision to fail over to the first charge on site 2. Target: 30 minutes.

Let the left side cycle through all three scenarios before you speak: only the first one is solved by replication inside the cluster. The second site is the backup, but the copy is asynchronous, so the gap in the dashed box is data you lose if site 1 dies now: that gap is your RPO. RPO and RTO are business numbers; ask the billing owner for them before you choose a tool. Ask the room: for an MQ estate, what is your RPO today, and has anyone ever measured it?
Topic 4 · Confluent Replicator and multi-datacenter replication

LicenceConfluent EnterpriseApache Kafka, open sourceConfluent Platform Enterprise, Confluent Cloud

Replicator is just another connector: it consumes from one cluster and produces into another, so it needs credentials on both, and anyone who can read its configuration can read the source password. Point at the lower lane: the shared Connect cluster is attached to Platform, so it can only write into Platform, which is why the copy to site 2 uses MirrorMaker 2 on your VM. Mention that MirrorMaker 2 renames topics with the source cluster's alias by default unless you choose the identity policy. Ask: active-passive or active-active for billing, and who decides when to fail over?
Topic 5 · Migration considerations: Apache Kafka → Confluent Kafka

Three ways to move: replicate, dual-write, or big bang

StrategyBilling pauseRisk to watchRollbackApplication change
Replicate, consumers firstShort: the consumer switchDuplicates: detect them by cdrIdPoint clients back: Apache still has everythingClient configuration only
Dual writeNoneThe two copies drift when one write failsEasy while both are writtenCode in every producer
Big bangThe whole copy and restartEverything happens in one windowSlow: restart the old platformClient configuration only
Data migration, client cutover and dual write are the three things the outline asks you to weigh. Point at the green bars: in the first strategy consumers move to Confluent while Apache is still being replicated, so billing pauses only for the switch, and Apache stays complete for the rollback. Dual write avoids the pause but puts migration logic in every producer, and the two copies can quietly drift. Ask: with the capstone's limits, a 5-minute billing pause and a 15-minute rollback, which strategy would you defend?
Topic 5 · Data migration and client cutover

Cut over consumers first, and decide where they start

Client settingApache Kafka todayConfluent Platform

Every step has a gate with a number: no consumer moves until the replication lag is zero, and no producer moves until consumers are healthy on the new cluster. The offset decision is the step people forget: a new group with no offsets falls back to auto.offset.reset, which you saw in Module 9 skips CDRs at latest and re-bills them at earliest. Verify with end offsets and the set of CDR IDs; TelcoPulse's chargeId is built from topic, partition and offset, so it cannot be compared across clusters. Best practices · Application developers integrating with Kafka

Developer guardrails: make the safe path the default

① Produce

acks=all and idempotence on. Key by MSISDN to keep per-subscriber order. Handle a failed send callback; never "log and continue".

② Contract

Avro or JSON Schema in Schema Registry. Defaults on new fields. Test compatibility in CI; set auto.register.schemas=false in production.

③ Consume

Commit after processing. Make processing idempotent by cdrId. Park poison pills on a dead-letter topic. Close the consumer on shutdown.

④ Run

Settings per environment, not in code. One credential per application. Set client.id, expose client metrics, ask the platform team for topics.

This slide is for the teams who write the producers and consumers; most message loss in Module 9 started in their code, not on the brokers. Walk the four zones in the order a CDR crosses them, and point out that TelcoPulse already does several of these: profiles per environment, a cdrId in every record, and at-least-once billing with a chargeId to spot duplicates. Turning off auto.register.schemas in production means only your pipeline registers schemas, after the compatibility check. Ask: which of these would you put in a pull-request checklist for every Kafka client?
Best practices · Kafka administration for admins and ops teams

Ops guardrails: everything as code, everything rehearsed

Design

RF 3, min ISR 2 for business topics. Retention longer than your longest consumer outage. A prefix per team. Disks below 70 %.

Change

Topics and bindings as code, reviewed and repeatable. Rolling restarts one broker at a time; throttle every reassignment.

Access

Narrowest role per application, proven with deny tests. Quotas on shared clusters. Rotate keys with no downtime.

Run

Alert on lag, under-min-ISR and offline partitions, each with a runbook. Measure RPO and RTO in a drill. Blameless reviews.

This is the course in one loop, for the people who run the cluster. Each card points back to a module: design to Modules 3 and 5, change to Modules 2 and 5, access to Module 7, run to Modules 8 and 9. The two words that matter are code and rehearsed: a change nobody can repeat, or a failover nobody has timed, is a risk you have not measured yet. Ask: which step of this loop does your MQ team do well today, and which one has never been rehearsed?

Wrap-up

Key takeaways, and a quick self-check

01Connectors, not code

Managed on Cloud, your own workers on Platform. Delete Cloud connectors when you are done.

02Schemas are the contract

A 4-byte ID in every record. Under BACKWARD, consumers deploy first and new fields need defaults.

03ksqlDB is a Kafka app

04RF 3 is not a backup

A second site with a measured RPO and RTO covers deletes, bad data and a lost site.

Developers: keyed, idempotent, schema-checked. Ops: as code, least privilege, rehearsed.

click to revealUnder BACKWARD, the producers ship schema v2 before the consumers upgrade. What can break?
Old consumers meet v2 records. BACKWARD only promises that new readers read old data, so consumers upgrade first.
click to revealSomeone deletes lNN.cdr.voice by mistake. Does RF 3 bring it back?
No: all three replicas are deleted. Only a copy on another cluster, or re-producing from the source, recovers it.
click to revealWhy not run Replicator on the shared Connect cluster to copy Platform to site 2?
Replicator runs in the destination's Connect. That Connect is attached to Platform, so it can only write into Platform.
click to revealCutover: the new billing group on Platform has no committed offsets. What do you do first?
Set its start position on purpose, from translated offsets or a timestamp. The default skips or re-bills CDRs.
