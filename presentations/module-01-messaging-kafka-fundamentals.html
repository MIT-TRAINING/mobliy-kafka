Topic 1 · Messaging recap

Why messaging? Decouple the systems that talk

Before Point-to-point integration

After A central event backbone

1Time

The sender doesn't wait. The receiver can be down and catch up later.

2Space

The sender doesn't know who receives, or where they run.

3Rate

Bursts are absorbed. Fast producers don't overwhelm slow consumers.

4Technology

Java, Python, mainframe, DB: they share a message format, nothing else.

Ask the room: how many point-to-point interfaces does your billing system have today? The N×M to N+M argument is why an event backbone exists at all.
Topic 1 · Messaging recap

Two classic models: queue vs publish–subscribe

Point-to-point queue

Each message goes to exactly one consumer. Competing consumers share the work.

IBM MQ local queue · JMS queue · work distribution, commands

Publish–subscribe topic

Each message goes to every subscriber. Each gets its own copy.

IBM MQ topics · JMS topics · notifications, fan-out
Kafka does both. Consumers in the same group share partitions like a queue. Different groups each get every message, like pub/sub. More on slide 9.
Watch the colours: on the left, each colour lands on ONE consumer. On the right, each colour lands on ALL of them. Kafka's consumer groups combine both.
Topic 1 · Comparison with IBM MQ

IBM MQ is a mailbox. Kafka is a ledger.

Mailbox: read = remove

Ledger: read = move a bookmark

MQ admins: queue depth ≈ consumer lag. Kafka's disk always fills up to retention, so disk usage tells you nothing about consumer health.
DimensionIBM MQ / traditionalApache Kafka
Core abstractionQueue of messagesPartitioned, append-only log
ReadingDestructive: removed on ackNon-destructive: kept until retention
DeliveryBroker pushes / hands outConsumer pulls in batches
Who tracks positionBroker, per messageConsumer group, one offset per partition
ReplayNot nativeReset offsets and re-read
OrderingPer queuePer partition
ScalingScale the queue manager upAdd partitions and brokers
Throughput~10³–10⁴ msg/s per QM~10⁵–10⁶ msg/s per cluster
Best fitTransactions (XA), commands, request/replyEvent streams, fan-out, replay, pipelines
This is the slide that saves MQ admins the most pain. Three questions people ask in week one: "why is the message still there?", "why can't more consumers go faster?", "why did ordering break?" The ledger model answers all three.

Topic 3 · The Kafka ecosystem

The cast: producers, brokers, topics, partitions, consumers

Producer

App that writes events to a topic. It picks the partition, usually from the key.

Broker

A Kafka server. Stores partitions on disk and serves clients on :9092.

Topic

A named stream of events, e.g. cdr.voice. Logical only, never stored whole on one broker.

Partition

An ordered, append-only log. The unit of scale, ordering and replication.

Consumer group

Consumers that share the work of reading a topic. Each group keeps its own offsets.

A topic is a logical name; partitions are physical. Topic cdr.voice here has 3 partitions spread over 3 brokers, which is how Kafka scales out. Producers never talk to "the topic"; they write to a partition leader.
Topic 3 · Topics & partitions

The key picks the partition. The partition keeps the order.

Same key → same partition. Every event for one subscriber stays in order.

Order is per partition, never across the whole topic.

No key? Records are spread across partitions in batches (sticky partitioner).

Adding partitions later remaps keys. Size topics up front (Module 3).

Colour = subscriber (MSISDN key). call-start and call-end for 001 always land in P1, in order. If you need global order you need ONE partition, and then you give up parallelism.
Topic 3 · Consumers & consumer groups

Consumer groups: queue inside, pub/sub across

1

Within a group, one partition → one consumer

That's how Kafka keeps per-partition order while scaling out.

!

More consumers than partitions = idle consumers

C4 gets nothing. Partitions cap parallelism.

2

Every group reads everything

billing and fraud each see all records, at their own pace, with their own offsets.

↻

Rebalance

When a consumer joins, leaves or crashes, the group reassigns partitions (Module 4).

MQ mapping: a group ≈ a durable subscription. Several consumers in it ≈ competing consumers on a queue.
Classic interview question: 3 partitions, 4 consumers in a group, how many are busy? Three. Want more throughput? Add partitions first, then consumers.
Topic 4 · Architecture: cluster design & replicas

Replication: one leader, several followers, per partition

ISR: in-sync replicas

The leader plus the followers that are caught up. If the leader's broker dies, the controller promotes a follower from the ISR, so no committed data is lost.

Durability baseline

3replication.factor
2min.insync.replicas
allacks

You survive one broker loss with no data loss and no write outage.

$ kafka-topics.sh --describe --topic cdr.voice Partition: 0 Leader: 1 Replicas: 1,2,3 Isr: 1,2,3 Partition: 1 Leader: 2 Replicas: 2,3,1 Isr: 2,3,1 Partition: 2 Leader: 3 Replicas: 3,1,2 Isr: 3,1,2
Leaders are spread so every broker does its share of the work. Clients produce to and consume from leaders; followers just fetch. Broker failure and reassignment are hands-on in Module 5; acks and min.insync.replicas are tested in Module 3.
Topic 4 · Architecture: offsets

Offsets: four markers every admin must read

Log start offset: oldest record still on disk. It moves forward as retention deletes segments.

Committed offset: where a group resumes. Stored per group and partition in __consumer_offsets.

High watermark: replicated to all ISR. Consumers only read below it.

Consumer lag: HW − committed. It's the #1 health metric (Module 8), your new "queue depth".

Offsets are sequential per partition and never reused. In Lab 02 learners will see CURRENT-OFFSET, LOG-END-OFFSET and LAG columns in kafka-consumer-groups.sh --describe. Map them to this picture.
Topic 5 · Message retention & compaction

How data leaves the log: delete or compact

cleanup.policy=delete Time/size retention

Old segments are dropped once they pass retention.ms (default 7 days) or retention.bytes, consumed or not.

Use for event streams: cdr.voice, logs, clickstreams

cleanup.policy=compact Keep latest per key

The log cleaner keeps only the newest value for each key. A null value (tombstone ∅) deletes the key.

Use for state: subscriber profiles, config, __consumer_offsets
Retention is per segment, not per message. There is no per-message TTL like MQ expiry. Only the active segment is written to, and it is never deleted. Lab 03 shows both policies with a 15-second retention check.
Topic 6 · ZooKeeper vs KRaft

Metadata moved inside Kafka: goodbye ZooKeeper

Legacy ZooKeeper mode

Today KRaft mode

2021 · 2.8KRaft early access
2022 · 3.3KRaft production-ready
2023 · 3.5ZooKeeper deprecated
2024 · 3.9Last ZK release, the migration bridge

Admin takeaways: new clusters are KRaft (Kafka 4.x, Confluent Platform 8.x). Old --zookeeper flags no longer work; use --bootstrap-server. ZK clusters must migrate on 3.x (ideally 3.9) before moving to 4.x. New object to monitor: the controller quorum (kafka-metadata-quorum.sh).

Wrap-up

Key takeaways, and a quick self-check

01Kafka is a log

Reading doesn't delete. Retention or compaction does.

02Partitions rule

They're the unit of order, parallelism and replication. The key picks the partition.

03Groups = queue + pub/sub

Queue inside a group, pub/sub across groups. Consumers beyond the partition count sit idle.

04Watch the offsets

Know log start, committed, HW and LEO. Lag is the health signal.

05Replicate for safety

RF 3 · min.insync.replicas 2 · acks=all. Leaders are elected from the ISR.

06KRaft only

Metadata lives in __cluster_metadata and a Raft quorum. No ZooKeeper in 4.x.
