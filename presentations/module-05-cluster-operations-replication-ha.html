Topic 1 · Adding and removing brokers

A new broker joins the cluster empty

A unique node.id. On the shared cluster, the controllers are 1–3 and the brokers are 11–14.

The same cluster ID. Read it with kafka-cluster.sh cluster-id, then run kafka-storage.sh format -t <id> on the new disk.

The same quorum. Copy controller.quorum.voters from the other brokers. The broker registers with the controllers when it starts.

Its rack. Set broker.rack to its availability zone so that replica placement stays rack-aware.

Walk through the right-hand steps: format, start, register, and then nothing happens to existing data. Kafka only places replicas when a partition is created, so broker-14 picks up new topics but never takes over old ones by itself. Apache Kafka has no built-in rebalancer, which is why the next slide exists; Confluent's Self-Balancing Clusters in Module 6 automate it. Ask: a broker was added on Monday, so why is it still at 2% disk on Friday?
Topic 1 · Partition reassignment · kafka-reassign-partitions.sh

A reassignment is a plan you generate, execute, verify

$ cat topics.json {"version":1,"topics":[{"topic":"l07.cdr.voice"}]} $ kafka-reassign-partitions.sh --bootstrap-server $APACHE --command-config $CFG \ --topics-to-move-json-file topics.json --broker-list 11,12,13,14 --generate Current partition replica assignment # copy this JSON to rollback.json Proposed partition reassignment configuration # copy this JSON to plan.json # the trainer runs this step: it needs Alter on the cluster $ kafka-reassign-partitions.sh … --reassignment-json-file plan.json --execute --throttle 50000000 $ kafka-reassign-partitions.sh … --reassignment-json-file plan.json --verify Reassignment of partition l07.cdr.voice-1 is completed.
--generate only reads metadata and proposes a plan, so it is safe to run as often as you like; it changes nothing. Always keep the "Current" JSON as rollback.json, because it is the only record of where the replicas were. On the shared cluster you generate and verify, and the trainer executes, because --execute needs Alter on the cluster and that would also let you change ACLs. Ask: why might you edit plan.json by hand instead of using the proposal as it is?
Topic 1 · Cluster balancing · throttled reassignment

A move adds the new replica first, then drops the old one

OptionUse it withWhat it does
--throttle <bytes/s>--executeCaps the copy rate for the moving replicas, so client traffic keeps its bandwidth
--additional--executeChanges the throttle of a running reassignment, or adds partitions to it
--verifythe same plan.jsonReports progress and removes the throttle once every partition is done
--cancelthe same plan.jsonStops the moves still in progress and puts those partitions back on their original replicas
Kafka never moves a replica in place: it adds the new replica, waits until it is in sync, and only then removes the old one. While that happens the partition has more replicas than its replication factor, so the copy costs disk and network on both brokers. Without --throttle, a large move can saturate the leaders and slow every producer on them. Ask: if latency climbs during a big move with no throttle, which option do you reach for?
Topic 1 · Adding and removing brokers

Remove a broker by draining it first

!
Common trap: stopping the broker first. Every partition that had a replica there becomes under-replicated, one more failure takes those partitions below min.insync.replicas, and any RF 1 topic goes offline. In KRaft, a stopped broker stays registered and fenced until you run kafka-cluster.sh unregister.
Draining is the add-a-broker workflow in reverse: generate a plan with a broker list that leaves 14 out, execute it, and verify until nothing is left on 14. Only then stop the process and unregister its ID, so tools and dashboards stop showing a dead broker. Because 14 shares rack a with 11, its replicas can only go back to 11 without breaking rack awareness. Ask: how do you prove broker-14 holds nothing before you stop it?
Topic 2 · ISR (in-sync replicas)

In sync means caught up recently, not identical

ISR size (RF 3, min ISR 2)acks=all writesReadsFind these partitions with kafka-topics.sh --describe
3 · healthyacceptedyes—
2 · at min ISRaccepted, no spareyes--under-replicated-partitions, --at-min-isr-partitions
1 · under min ISRrejected: NOT_ENOUGH_REPLICASyes--under-min-isr-partitions
no leaderrejectedno--unavailable-partitions
Followers pull from the leader exactly like consumers do. A follower stays in the ISR as long as it has caught up to the leader's log end within replica.lag.time.max.ms, 30 seconds by default. The high watermark is the highest offset every ISR member has, and consumers only see records below it, which is why acks=all and min.insync.replicas from Module 3 work together. Ask: with RF 3 and min ISR 2, how many brokers can you lose before billing's producer starts failing?
Topic 2 · Leader election

When a leader dies, the controller promotes an in-sync follower

Only the ISR can lead

unclean.leader.election.enable=false is the default. With no ISR member left, the partition goes offline instead of losing acknowledged writes.

A clean stop hands over first

A broker stopped with SIGTERM does a controlled shutdown: its leaderships move before it exits. kill -9 leaves them to the session timeout.

Leadership drifts back

The first replica in the list is the preferred leader. With auto.leader.rebalance.enable=true, the controller returns leadership to it within leader.imbalance.check.interval.seconds (300 s).

Clients ride through

Producers get the retriable NOT_LEADER_OR_FOLLOWER, refresh their metadata and retry inside delivery.timeout.ms (Module 4).

In KRaft, brokers heartbeat to the active controller every 2 seconds, and a broker that misses heartbeats for broker.session.timeout.ms, 9 seconds by default, is fenced. The controller then picks the next live replica that is in the ISR and pushes the new leader to every broker through the metadata log. Turning on unclean leader election trades lost CDRs for availability, and for billing data that is almost never the right trade. Ask: why does a planned stop with systemctl cause a shorter blip than a crashed instance?
Topic 2 · Handling broker failures

Triage a broker failure: quorum first, then partitions

# 1. Is the controller quorum healthy? (leader, high watermark, voters) $ kafka-metadata-quorum.sh --bootstrap-server $APACHE --command-config $CFG describe --status # 2. Which partitions are hurt, and how badly? $ kafka-topics.sh --bootstrap-server $APACHE --command-config $CFG --describe --under-replicated-partitions $ kafka-topics.sh … --describe --under-min-isr-partitions # acks=all writes are failing here $ kafka-topics.sh … --describe --unavailable-partitions # no leader at all: reads fail too # 3. Bring the broker back, wait for URP = 0, then restore balance if needed (trainer) $ kafka-leader-election.sh --bootstrap-server $APACHE … --election-type PREFERRED --all-topic-partitions
Check the controllers first: if the quorum has no leader, no partition can change leader and nothing else you do will help. Then sort the damage, because under-replicated means less safety, under min ISR means producers are failing, and unavailable means an outage. A restarted broker truncates to the high watermark and fetches from the leaders until it is back in the ISR. Ask: the broker's disk is gone for good, so what do you do with its replicas?
Topic 3 · Rolling restarts

One broker at a time, and wait for URP = 0

Why one at a time. With RF 3 and min ISR 2, every partition can lose exactly one replica and keep accepting writes.

The gate. Wait for --under-replicated-partitions to return nothing before you touch the next broker.

Stop cleanly. Use systemctl stop kafka (SIGTERM) so leaderships move first. Never kill -9 during maintenance.

Controllers too. Three voters survive one down. Restart them one at a time and check describe --status in between.

A rolling restart is how you apply a static config change, patch the OS or upgrade Kafka without an outage. The gate is the whole discipline: if you restart broker-12 while broker-11 is still catching up, some partitions have two replicas down and drop below min ISR. Keep your Module 4 producer running during the drill and watch it ride through with retries but no errors. Ask: what happens if you restart two controllers out of three at once?
Topic 3 · Upgrade considerations

Upgrade in two steps: binaries, then metadata.version

Check before you startWhy it matters for Kafka 4.x
ZooKeeper cluster?4.x has no ZooKeeper. Migrate to KRaft on 3.9 first, then upgrade (Module 2).
KRaft 3.3 – 3.9Can roll straight to 4.x. Read the upgrade notes for removed configs and flags.
Java runtimeBrokers and tools need Java 17 or later. Clients need Java 11 or later.
Very old clients4.0 dropped old protocol versions, so clients older than 2.1 can no longer connect. Find them before upgrading.
Phase one is just a rolling restart with new binaries, so every rule from the previous slide applies, and until you finalize you can still roll back to the old version. Phase two raises metadata.version with kafka-features.sh, and only then do features that change the metadata format switch on; treat it as one-way and run it only after a soak period. Check kafka-features.sh describe before and after so you know which version is finalized. Ask: why does Kafka separate "new code running" from "new feature level enabled"?
Topic 4 · Cluster capacity planning

Size from the peak: rate × size × RF × retention

ResourceWhat drives itThis example
DiskRate × size × retention × RF, plus headroom for growth and moves≈ 6.5 TB per broker
Network inProducer traffic plus follower fetches for replication10 + 20 MB/s cluster-wide
Network outEvery consumer group reads the full stream, plus replication3 groups: 30 + 20 MB/s
PartitionsPeak consumer parallelism and the per-partition rate you measured in Module 4Measure, don't guess
Start from the business number, the peak CDR rate and its average size, not from a broker count. Multiply by replication factor for disk writes and by the number of consumer groups for network out, because each group, such as billing, fraud and the data lake, reads the full stream again. The 70% line leaves room for a reassignment, a retention change and growth. Ask: marketing wants 30-day retention instead of 7, so what does that do to the disk per broker?
Topic 4 · Cluster capacity planning · failure headroom

Size for the day a broker is missing

Plan for N−1. With 4 brokers, the survivors carry 4/3 of the load. Check that number, not the everyday one.

Balance the racks. Rack a holds 11 and 14. Losing it keeps every partition writable, but halves the brokers.

Partitions are not free. Each replica costs file handles, memory and recovery time after a restart.

Watch the trend. Disk %, network and request latency per broker drive the next expansion (Module 8).

Rack-aware placement guarantees that losing one rack removes at most one replica of each partition, so with min ISR 2 everything stays writable. Capacity is a different question: the remaining brokers take the leaderships, the client traffic and the catch-up work. On the shared cluster, rack a has two brokers and the other racks have one each, which is exactly the uneven layout to avoid in production. Ask: how would you change this cluster so that losing any one zone leaves at least two-thirds of the brokers?

Wrap-up

Key takeaways, and a quick self-check

01New brokers start empty

Only new partitions land on them. Move existing ones with a reassignment.

02Generate, execute, verify

Keep rollback.json, throttle the copy, and let --verify clear the throttle.

03Drain before you remove

Reassign the replicas off, stop the broker, then unregister its ID.

04The ISR is the safety net

acks=all with min ISR 2, and unclean election stays off.

05One node at a time

Gate every restart on URP = 0. Roll the binaries before you raise metadata.version.

06Size for N−1

Rate × size × RF × retention, with headroom for a lost broker or rack.
