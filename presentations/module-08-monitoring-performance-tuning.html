The model · what every Kafka cluster tells you

Watch four vital signs: throughput, latency, lag and health

① Throughput

MQ: RESET QSTATS MSGSIN / MSGSOUT. Kafka: bytes and records in and out per second, per broker and per topic.

② Latency

MQ: DIS CHSTATUS NETTIME, XQTIME. Kafka: how long a produce or fetch request takes. Read the p99, not the average.

③ Lag

MQ: CURDEPTH and MSGAGE. Kafka: the messages a consumer group has not committed yet. Every group has its own lag.

④ Health

MQ: queue manager and channel status. Kafka: under-replicated and offline partitions and the KRaft quorum, as in Module 5.

Keep these four numbers in mind for the rest of the day: every tool you see today is a different window onto them. The big difference from MQ is lag: a queue has one depth, but a Kafka topic keeps its messages, so each consumer group has its own distance from the end of the log. Point at probe three: the gap between billing's committed offset and the log end is the lag. Ask: if fraud reads the same topic and is fully caught up, is the topic healthy?
Topics 1, 2 and 5 · where each platform keeps its metrics

The same signals take three different collection paths

i
MQ admins: this is the choice you already know from MQ monitoring. You can build it yourself from statistics and event messages, or use a product that collects them for you. On Kafka the raw material is JMX, and Confluent's tools collect it for you.
Read the three lanes from left to right. On Apache Kafka you own the whole pipeline: the exporter agent, Prometheus and Grafana. The shared Apache lab cluster runs the JMX exporter on port 7071 for exactly that. On Confluent Platform the collector, store and UI come in one product, Control Center 2.x, and Health+ adds a hosted copy. On Cloud you never see a broker, so the Metrics API is your only window. Ask: on which lane does your team carry the pager for the monitoring system itself?

Topic 1 · Confluent Control Center alerting

An alert is a condition that lasts, sent to an owner

Alert on what users feel

Consumer lag, offline partitions, under-replicated partitions. Keep CPU and heap on the dashboard, not on the pager.

Require a duration

A burst of CDRs at midnight is normal. Use "above the threshold for 5 minutes" so spikes that clear on their own stay quiet.

Send it to an owner

Lag on l07.billing goes to the billing team, and offline partitions go to the platform on-call.

Test it on purpose

An alert that has never fired is only a guess. You will make yours fire in Lab 02.

In Control Center an alert has two halves: a trigger, which is a condition on a cluster, broker, topic or consumer-group metric, and an action, which is where the notification goes. In 2.x the embedded Alertmanager sends the notifications. Follow the cursor: crossing the line does nothing yet, staying above it for five minutes fires the alert, and dropping back below it sends a resolved notice. Ask: what threshold would you choose for billing lag, and how did you pick the number?
Topic 3 · Consumer lag, the signal your users feel

Lag = log end − committed offset: read it as a trend

$ kafka-consumer-groups.sh --bootstrap-server $CP --command-config $CFG --describe --group $ME.analytics GROUP TOPIC PARTITION CURRENT-OFFSET LOG-END-OFFSET LAG l07.analytics l07.cdr.voice 0 41210 43010 1800 l07.analytics l07.cdr.voice 1 40987 42987 2000 l07.analytics l07.cdr.voice 2 41500 42500 1000 # total lag 4,800 · CONSUMER-ID, HOST and CLIENT-ID columns trimmed for the slide
You have read this table since Module 4: lag is counted per partition, and the group's lag is the sum. One number tells you little. The trend tells you everything, so always look at lag over time, which is what Control Center and the Metrics API give you. To turn offsets into time, divide by the consume rate: 4,800 messages at 400 per second is about 12 seconds behind, which matters more to billing than the raw count. Ask: if only partition 1 keeps climbing, what would you suspect before adding consumers?
Topic 2 · Confluent Metrics API

No broker to log in to: on Cloud you query metrics

# a Cloud API key, not a cluster key $ confluent api-key create --resource cloud $ cat received_bytes.json { "aggregations": [{ "metric": "io.confluent.kafka.server/received_bytes" }], "filter": { "field": "resource.kafka.id", "op": "EQ", "value": "lkc-…" }, "granularity": "PT1M", "intervals": ["2026-10-08T09:00:00Z/PT1H"] } $ curl -s -u "$CLOUD_KEY:$CLOUD_SECRET" \ -H 'Content-Type: application/json' -d @received_bytes.json \ https://api.telemetry.confluent.cloud/v2/metrics/cloud/query # → {"data": [{"timestamp": …, "value": …}, …]}, one point per minute # other metrics: sent_bytes · received_records · retained_bytes # active_connection_count · consumer_lag_offsets
The Metrics API is the only way to get numbers out of a Confluent Cloud cluster: there is no JMX and no broker to log in to. It needs a Cloud API key, the --resource cloud kind from Module 6, and not the cluster key your clients use. Use query for questions like "what was ingress between 9 and 10?", and point Prometheus or Datadog at the export endpoint for continuous dashboards. Ask: which identity should own the key that your Prometheus server uses, and what is the smallest role it needs?

Throughput says how much work the cluster does, and latency says how hard that work is. Follow the dot through one produce request with acks=all: the longest part is usually the remote time, waiting for the followers, which is the price of durability you chose in Module 3. A high request-queue time with low handler idle percent means the brokers are saturated, not slow. On Cloud you cannot read broker JMX, so the client metrics in the right column become your latency signal. Ask: produce p99 jumps but bytes in are flat, so which part of this bar do you check first?
Topic 4 · Performance considerations and scaling in Confluent-managed clusters

At a limit, Confluent throttles instead of failing

!
Common trap: throttling looks like slowness, not failure. The broker delays its replies, produce-throttle-time-avg rises above zero and latency climbs, but nothing is logged as an error. The shared Apache cluster's per-learner quotas behave the same way.
On Cloud you no longer size brokers. You pick a cluster type and capacity units: elastic eCKUs grow and shrink for you, while Dedicated CKUs change only when you change them. Either way, demand above the limit is throttled, so the producer keeps working but slows down. On Platform, scaling is still your job: add a broker, and Self-Balancing, which is on in the lab cluster with confluent.balancer.enable=true, moves partitions without the manual reassignment you did in Module 5. Ask: which of the three panels gives you the most predictable bill, and which gives you the most predictable latency?
Topic 4 · Performance tuning: the levers you control

Most tuning happens in the clients and the partition count

SymptomLikely causeLever
High request rate, low throughputTiny batches (linger.ms=0, many partitions)Raise linger.ms to 10–20 ms and batch.size, and add compression.type
send() blocksProducer buffer full, because the broker or network is too slowFix broker throughput first, then raise buffer.memory
Lag climbs, consumers busyNot enough parallelismMore partitions and consumers, never more consumers than partitions
Throttle time above zeroQuota or capacity limit reachedRaise the quota or capacity. Retries will not help.
You measured the left half yourself in Module 4 with kafka-producer-perf-test.sh: the same records, sent in batches and compressed, cost the brokers far fewer requests. The right half is the hard limit on consumers: one partition is read by at most one member of a group, so a seventh consumer only waits. Tune in this order: measure, change one client setting, measure again, and only then pay for more capacity. Ask: your billing group has 6 consumers on 6 partitions and lag still climbs, so what are your options?

Wrap-up

Key takeaways, and a quick self-check

01Four vital signs

Throughput, latency, lag and health. Every tool today is another window onto them.

02Three stacks

JMX and Prometheus you build, Control Center and Health+ on Platform, the Metrics API on Cloud.

03Lag is a trend

Log end minus committed offset, per partition and per group. Divide by the consume rate to get time behind.

04Alerts need time and an owner

A condition held for a duration, sent to the team that can fix it, and tested on purpose.

05Latency has parts

Queue, local, remote, response: the biggest part points to the bottleneck.

06Limits throttle

At a quota or capacity limit, clients slow down. Watch the throttle time, then scale or tune.

click to revealOne group has lag 50,000 on a topic, another has lag 0. Is the topic unhealthy?
No. Lag belongs to a group: the slow group's consumers are behind, not the topic.
click to revealWhy alert on "lag above N for 5 minutes" rather than "lag above N"?
Bursts are normal. The duration filters out spikes that clear on their own.
click to revealWhich key does the Metrics API need?
A Cloud API key (--resource cloud), not the cluster key your clients use.
click to revealProduce p99 is high and remote time dominates. Where do you look?
At the followers: a slow replica or the network between brokers, because acks=all waits for the ISR.
