Topic 3 · Authentication and authorization overview · the mental model

Every request crosses three gates

Encrypt. Like SSLCIPH on an MQ channel: TLS on a Kafka listener, client to broker and broker to broker.

Authenticate. Like CHLAUTH plus MCAUSER: SASL, mTLS or an API key decides the principal.

Authorize. Like setmqaut and the OAM: ACLs or RBAC role bindings decide what the principal may do.

Audit. Like MQ authority events: Confluent writes each decision to an audit-log topic.

This is the model for the whole module: three independent gates, each with its own configuration. Follow the dot. TLS only hides the bytes, authentication only produces a name, and only authorization says yes or no, so a perfectly encrypted connection can still be denied. Ask: if a client gets "SaslAuthenticationException", which gate failed, and what about "TopicAuthorizationException"?
Topic 5 · The Apache Kafka baseline: SASL, SSL and ACLs

On Apache Kafka, access is a list of ACL rules

# 1 · a SCRAM user, stored in the KRaft metadata $ kafka-configs.sh --bootstrap-server $BS \ --command-config admin.properties --alter \ --entity-type users --entity-name l07 \ --add-config 'SCRAM-SHA-512=[password=…]' # 2 · prefix ACLs, as on the shared cluster $ kafka-acls.sh --bootstrap-server $BS \ --command-config admin.properties --add \ --allow-principal User:l07 --operation All \ --topic l07. --resource-pattern-type prefixed # … the same for --group l07. and # --transactional-id l07. # 3 · read back what a principal may do $ kafka-acls.sh --bootstrap-server $BS \ --command-config admin.properties \ --list --principal User:l07
This is exactly how the shared Apache cluster from Modules 3 to 5 was built, by infra/cluster/scripts/bootstrap-security.sh: one SCRAM-SHA-512 user per learner, and four prefix ACLs each. Walk through the six parts of one rule, then follow the two requests. There is no "deny everything else" line because the authorizer denies anything no rule allows. Ask: how many ACL lines would Mobily need for 200 applications, each with its own topics, groups and transactional IDs?
Topic 1 · Confluent RBAC (Role-Based Access Control)

RBAC grants a role, not a list of operations

Roles are bundles

Confluent defines the operations behind each role. You pick DeveloperRead, not Read plus Describe.

Scopes inherit

A role on an environment covers every cluster and topic inside it. Bind as low as the job allows.

One model for the platform

The same bindings cover Kafka topics, Schema Registry subjects, Connect connectors and ksqlDB clusters.

Central and delegable

Bindings live in one place. On Platform you can bind LDAP groups, and a ResourceOwner can grant access to what it owns.

Read the binding left to right as a sentence: "this principal has this role, at this scope, on this resource". The role is the big difference from ACLs: Confluent maintains the list of operations, so when Kafka adds an operation you do not chase every rule. ACLs still exist on Confluent and are checked alongside RBAC, which you will see in the comparison at the end. Ask: in MQ terms, is a role closer to an OAM group or to a single setmqaut command?

Topic 1 · Confluent RBAC · least privilege for the CDR pipeline

One identity per component, the narrowest role that works

!
Common trap: a consumer needs DeveloperRead on its consumer group as well as the topic, and a transactional producer needs DeveloperWrite on its TransactionalId. Miss one and the error names a resource you never thought about.
This is the access matrix you build in capstone phase B6.1, drawn for three components. Each service account gets only the roles its component uses, so a compromised billing key can read CDRs but never write or delete them. Watch the red attempt: billing is authenticated, but authorization refuses the write. Ask: which identity in this picture would you give DeveloperManage to, if any?
Topic 2 · API keys and secrets management (Confluent Cloud)

An API key is a password for an identity that holds roles

# 1 · the identity (the lab pre-creates sa-$ME-app) $ confluent iam service-account create sa-l07-billing \ --description "billing consumer" # 2 · its roles, on prefixed resources $ confluent iam rbac role-binding create \ --principal User:$SA --role DeveloperRead \ --environment $ENV_ID --cloud-cluster $LKC \ --kafka-cluster $LKC \ --resource Topic:l07.cdr. --prefix # … and Group:l07.billing for the consumer group # 3 · its key, scoped to one cluster $ confluent api-key create --resource $LKC \ --service-account $SA --description "billing" # 4 · check what it can do $ confluent iam rbac role-binding list \ --principal User:$SA --environment $ENV_ID
The key never holds permissions itself: it only proves "I am this service account", and the account's role bindings decide the rest. That is why the user-owned key from Module 6 is dangerous for applications: it carries your EnvironmentAdmin rights and dies when your account is removed. The commands follow infra/confluent/scripts/cc-provision.sh, which pre-created sa-lNN-app for you. Ask: what happens to the application if you delete the service account but not the key?
Topic 2 · API keys and secrets management · the lifecycle

Secrets have a lifecycle: store, rotate, revoke

The secret is shown once

Confluent Cloud displays it only at creation. Store it at once, or delete the key and create another.

Never in git

Keep secrets in a vault or secrets manager. Properties files with secrets stay outside the repository (capstone B6.2).

Rotate with overlap

A service account can hold more than one key. Add the new key, roll the clients, then delete the old one.

On Platform: protect config files

confluent secret encrypts passwords inside server.properties and component configs.

Treat the key and secret like an MQ channel password or a certificate: they have an owner, a store and an expiry plan. The overlap in the middle of the timeline is the whole trick, because two valid keys mean clients can switch without an outage. Deleting the old key is also how you revoke a leaked secret, and it takes effect at once. Ask: where does your team keep application passwords today, and who can read them?
Topic 3 · Confluent Platform authentication · the shared lab cluster

On Platform, each listener picks how callers prove who they are

!
MQ admins: SASL PLAIN is not "plaintext". On the CLIENT listener the password travels inside TLS (SASL_SSL), and the broker checks it against LDAP. PLAIN over SASL_PLAINTEXT would expose it on the wire.
These are the real listeners of the shared Confluent Platform cluster from infra/guides/confluent-platform-cluster-connect.md. Each listener has its own protocol and its own way to authenticate: people come in with LDAP passwords, servers prove themselves with certificates, and the platform services carry short-lived tokens from MDS. Only 9092, 8090 and the service ports are open to your VM. Ask: why do the brokers and controllers use certificates rather than passwords to talk to each other?
Topic 3 · Confluent Platform authorization · MDS, RBAC and audit

MDS stores the role bindings; every broker enforces them

# log in to MDS with your LDAP user $ confluent login --url $MDS_URL \ --certificate-authority-path $CP_CA # the Kafka cluster ID that bindings refer to $ confluent cluster describe --url $MDS_URL \ --certificate-authority-path $CP_CA # your bindings: ResourceOwner on Topic:l07. # and Group:l07. (prefixed) $ confluent iam rbac role-binding list \ --principal User:l07 --kafka-cluster $CP_ID # as ResourceOwner, grant read-only on your prefix $ confluent iam rbac role-binding create \ --principal User:l08 --role DeveloperRead \ --kafka-cluster $CP_ID \ --resource Topic:l07. --prefix
You proved this in Module 6 Lab 03: the CLI, kafka-topics.sh and Control Center all hit one authorizer, and other.topic was refused by all three. The broker setting confluent.authorizer.access.rule.providers=CONFLUENT,KRAFT_ACL is why role bindings and ACLs work side by side. Denials do not go to kafka-authorizer.log; Confluent Server writes them to the confluent-audit-log-events topic. Ask: which identity would the trainer need to read that audit topic, and should learners have it?

Work through the layers from the outside in: first who can even reach the port, then whether the bytes are readable on the wire, then whether the disk is readable if a volume walks away. The Apache lab cluster deliberately runs SASL_PLAINTEXT inside the VPC, so SCRAM keeps passwords off the wire but the records themselves are not encrypted; production would add TLS. On Cloud most of this is done for you, but private networking and your own keys depend on the cluster type. Wrap-up

Key takeaways, and a quick self-check

01Three gates

Encrypt, authenticate, authorize: each one is configured separately, and each one fails with its own error.

02ACLs vs roles

ACLs list operations per principal. RBAC binds a predefined role at a scope, and both are checked together.

03Least privilege

One service account per component, Developer roles on prefixed topics, groups and transactional IDs.

04Keys belong to identities

An API key only proves who is calling. The owner's role bindings decide what the call may do.

05Secrets lifecycle

Shown once, kept out of git, rotated with two overlapping keys, revoked by deleting the key.

06Platform plumbing

LDAP passwords on 9092, mTLS between servers, MDS tokens on 8090, audit events in a topic.
