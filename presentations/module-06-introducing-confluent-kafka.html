Topic 1 · Confluent Platform overview

Confluent is Apache Kafka with rings around it

Same protocol. Your Module 4 Java clients and kafka-topics.sh connect unchanged. Only the connection file differs.

Confluent Server. The broker package is Apache Kafka plus enterprise features. Your server.properties knowledge carries over.

Separate services. Schema Registry, Connect and ksqlDB run as their own processes and talk to the brokers as clients.

Two deliveries. The same layers come as Confluent Cloud or as self-managed Confluent Platform (Topic 3).

Start at the core and work outwards: nothing you learned about partitions, replication or the ISR changes on Confluent. Confluent Server replaces the Apache broker binary and switches on extra features through ordinary broker properties, while the services in the next ring are separate JVMs you size and monitor. Confluent also ships a plain Apache Kafka broker package, so "Confluent" does not automatically mean "enterprise features". Ask: if you replaced your brokers with Confluent Server tomorrow, which of your Module 5 runbooks would still be valid?
Topic 1 · Confluent Platform architecture · the shared lab cluster

Inside the shared cluster: brokers, services and a UI

Controllers. Three KRaft voters, exactly as on the Apache cluster in Module 5. Confluent Platform 8.x has no ZooKeeper.

Brokers. Confluent Server on :9092, plus MDS and the REST API on :8090, which the CLI and Control Center use.

Services node. Schema Registry, Connect, ksqlDB and Control Center are clients of the brokers. They store their state in topics.

Identity. OpenLDAP users l01…l18. MDS maps them to RBAC roles on your lNN.* topics (Module 7).

This is the self-managed Confluent Platform you will use from today, built with cp-ansible as described in infra/LAB-SETUP.md. Trace a record from the lab VM to a broker, then show that every service on the right is just another Kafka client: Schema Registry keeps schemas in a topic and Connect keeps its offsets and configs in topics. MDS, the Metadata Service, is the piece that turns an LDAP login into permissions, which is why the CLI and Control Center log in through port 8090. Ask: which component on this diagram would you restart first if Control Center showed no data but producers still worked?

Topic 2 · Confluent vs Apache Kafka: licensing

Three licences, decided per component

Community is free, not open source

You can run and modify it in production at no cost. You cannot offer it as a competing hosted service.

Enterprise needs a licence key

Set with confluent.license. Without one, a 30-day trial runs. When it ends, Control Center and RBAC stop working.

Developer licence

Enterprise features free with no expiry, but only on a single-broker cluster: fine for a laptop, never for production.

Confluent Cloud

No licence keys. Features come with the cluster type and you pay for usage.

Licensing is decided per component, so one installation can mix all three tiers. The lab Confluent Platform runs on the built-in 30-day trial, which is why it was installed close to the course date; in production a missing renewal stops Control Center and RBAC, so track the licence expiry like a certificate expiry. Procurement will ask you this in every migration discussion. Ask: Mobily already runs Schema Registry on Apache Kafka, so which licence is that under, and does it need a subscription?
Topic 3 · Confluent Cloud vs self-managed Confluent Platform

Cloud or self-managed: who holds the wrench

Cloud cluster types. Basic, Standard, Enterprise and Dedicated differ in limits, networking and SLA. You get Basic, and the trainer uses Standard.

Cloud providers. Confluent Cloud runs on AWS, Azure or Google Cloud in the region you choose.

Self-managed installs. Packages or archives on VMs, cp-ansible, or Confluent for Kubernetes. The lab uses cp-ansible.

Same client API. Moving between them changes the connection file, not the code (capstone NFR-04).

The question is not which product is better but where the responsibility line sits. On Confluent Platform every layer is yours, including the rolling restarts and upgrades from Module 5. On Confluent Cloud the line moves up, and the broker settings you tuned in Module 3 are no longer yours to change. Ask: which of the five layers that move to Confluent does your team spend the most night-time hours on?

Topic 4 · Confluent CLI overview and authentication

One CLI, two kinds of login

# Confluent Cloud: SSO in a browser, or e-mail and password. --no-browser prints a URL to open on your laptop $ confluent login --save --no-browser $ confluent environment list # find the ID of env-l07 $ confluent environment use env-xxxxx $ confluent kafka cluster list $ confluent kafka cluster use lkc-xxxxx # Confluent Platform: log in to MDS on the brokers with your LDAP user $ confluent login --url $MDS # https://<cp broker>:8090 $ confluent context list # one context per login · switch with: confluent context use
The Confluent CLI is one binary that talks to both worlds; each login becomes a context, so check confluent context list before any destructive command. On Cloud, everything lives in a hierarchy: organization, environment, cluster, and the use commands set your defaults so later commands need fewer flags. On your lab VM there is no browser, so --no-browser prints a URL you open on your laptop, and --save keeps you logged in between sessions. Ask: what is the Cloud equivalent of the --bootstrap-server flag you typed in every Apache command?
Topic 4 · Confluent CLI authentication · control plane vs data plane

You log in; applications use API keys

$ confluent api-key create --resource lkc-xxxxx --description "l07 lab" # the secret is printed once: store it outside git $ confluent api-key use <API_KEY> # used by confluent kafka topic produce / consume $ cat ~/kafka/confluent.properties bootstrap.servers=pkc-xxxxx.<region>.<cloud>.confluent.cloud:9092 security.protocol=SASL_SSL sasl.mechanism=PLAIN sasl.jaas.config=org.apache.kafka.common.security.plain.PlainLoginModule required username="<API_KEY>" password="<API_SECRET>"; $ kafka-topics.sh --bootstrap-server $CC --command-config ~/kafka/confluent.properties --list
Separate the two planes clearly: your login manages things, an API key moves data. An API key is scoped to one cluster, and its secret is shown only once, so treat it like a password. Compare the properties file with your Module 4 apache.properties: SCRAM-SHA-512 becomes PLAIN over TLS, and the username is now an API key, which is why the same Java code runs unchanged. On Confluent Platform the equivalent is your LDAP user through MDS, and Module 7 replaces personal keys with service accounts. Ask: what happens to every running application if someone deletes the API key in the console?
Topic 5 · Confluent Control Center walkthrough

Control Center: the cluster on one screen

Overview. Health first: brokers online, under-replicated partitions and throughput, the Module 5 checks on one page.

Topics. Create and edit topics, browse messages, see the schema and every config value.

Consumers. Lag per group and partition, the view you build alerts on in Module 8.

Respects RBAC. Logged in as l07, you only see the resources your roles allow.

Open Control Center through the lab load balancer and log in with your LDAP user while the slide cycles. Map each page to a command you already know: Overview replaces kafka-topics.sh --under-replicated-partitions, and Consumers replaces kafka-consumer-groups.sh --describe. Since Confluent Platform 8.0, Control Center is released separately from the platform and keeps its metrics in Prometheus. On Confluent Cloud the equivalent pages are in the Cloud Console. Ask: which page would you open first when the billing team says their numbers are late?

Same topic verbs, over a REST API

Apache Kafka (Modules 2–3)Confluent CLINote

The Confluent CLI does not speak the Kafka protocol for topic management; it calls the REST API, which is why Confluent Platform commands need --url pointing at the embedded REST endpoint, or the CONFLUENT_REST_URL variable. On Confluent Cloud you choose partitions and topic configs, but replication factor and broker settings belong to Confluent. Capstone B5.1 asks you to map your whole Part A topic catalog onto this table. Ask: which of your Module 3 topic settings do you expect Confluent Cloud to refuse?
Topic 6 · Topic management via Control Center

In Control Center, a form does the same job

What the UI gives you

Message browsing, live throughput and lag per topic, and every config with its default next to it.

What the CLI gives you

Scripts you can review in git, re-run safely and apply the same way to every environment.

One cluster, one truth

Create in the UI, then describe in the CLI: both read the same topic metadata from the controllers.

Common trap

A delete is permanent in both tools. Check the context and the name: l07.cdr.voice is not l17.cdr.voice.

Demo the three steps live on the shared Confluent Platform cluster with your own prefix, because RBAC only lets you create topics under lNN. Point out that "Customize settings" shows the same configs you set with --config in Module 3, with the defaults inherited from the brokers. In production, teams usually create topics through reviewed scripts and use the UI to inspect, so the UI is for exploring and the CLI is for changes. Ask: which tool would you trust for a change at 2 a.m., and why?
Hands-on · Confluent Cloud and the shared Confluent Platform

Explore both, then create, inspect and delete a topic

# Lab 01 · explore Confluent Cloud and Confluent Platform $ confluent login --save --no-browser $ confluent environment use env-xxxxx # env-$ME $ confluent kafka cluster use lkc-xxxxx $ confluent kafka cluster describe # then open the Cloud Console and Control Center # Lab 02 · topic CRUD on Confluent Cloud $ confluent kafka topic create cdr.voice --partitions 6 \ --config retention.ms=604800000 --if-not-exists $ confluent kafka topic list $ confluent kafka topic describe cdr.voice $ confluent kafka topic update cdr.voice --config retention.ms=259200000 $ confluent kafka topic delete cdr.voice # … and on Confluent Platform: create $ME.cdr.voice in Control Center, then $ confluent kafka topic describe $ME.cdr.voice --url $MDS/kafka

Access and explore the Confluent cluster and Cloud Console

Log in to both contexts, select env-$ME and its cluster, then find brokers, topics and consumers in Control Center.

02

Topic create / list / describe / delete

Run the full lifecycle on Confluent Cloud with the CLI, then on Confluent Platform with Control Center, and compare the views.
