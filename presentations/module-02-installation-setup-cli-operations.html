Topic 1 · System requirements

Size the host for the page cache, not the heap

Where a broker's RAM actually goes

ResourceLab / devProduction start
CPU2 vCPU8–16 vCPU (compression, TLS)
RAM2–4 GB32–64 GB, mostly page cache
JVM heap512 MB–1 GB~6 GB, rarely more
Diskany local diskDedicated SSD/NVMe · XFS/ext4 · never NFS
Network1 Gbps10 Gbps+ (replication multiplies traffic)
ulimit -nOS default≥ 100,000 (segments + sockets)

Java 17+ for brokers

Kafka 4.x brokers need Java 17 or newer. Clients run on Java 11+. The Docker image bundles its own JVM.

Linux, synced clocks, DNS

Linux in production, NTP/chrony running, and every advertised hostname resolvable from every client.

The counter-intuitive point: a small heap plus lots of free RAM beats a huge heap. Kafka writes into the OS page cache and consumers reading the tail of the log are served from memory. Big heaps just mean longer GC pauses. Capacity planning in depth comes in Module 5.
Topic 1 · Installation options

Five ways to get a cluster. Same Kafka inside each.

Skills transfer. node.id, listeners, log.dirs, the controller quorum: the same properties drive every option. Only the packaging changes: a file on Linux, environment variables in Docker, a CRD on Kubernetes.
Ask: which of these do you run today? Labs use Docker Compose because it reproduces a real multi-broker topology (separate processes, ports and failures) on one machine. The shared AWS cluster from Module 3 is a Linux binary install. Confluent Platform and Confluent Cloud arrive in Module 6.
Topic 1 · Installing on Linux

The binary install: what production looks like

Two "logs": logs/ is the broker's own application log. Your data lives wherever log.dirs points.
# 1. Java 17+ is required for Kafka 4.x brokers $ java -version # 2. Download and extract the release $ curl -O https://downloads.apache.org/kafka/4.3.1/kafka_2.13-4.3.1.tgz $ tar -xzf kafka_2.13-4.3.1.tgz && cd kafka_2.13-4.3.1 # 3. A service user and a dedicated data directory $ sudo useradd --system --no-create-home kafka $ sudo mkdir -p /var/lib/kafka/data $ sudo chown -R kafka:kafka /var/lib/kafka/data # 4. Format storage (next slides), then run under systemd $ sudo systemctl enable --now kafka $ journalctl -u kafka -f

Never as root

A dedicated kafka user limits the blast radius.

systemd unit

Restart=on-failure and LimitNOFILE=100000.

Format first

A new node won't start until its storage is formatted.

This is how the shared AWS cluster is built and how most production clusters are run. The Docker image does exactly these steps for you. Put log.dirs on its own volume so a full disk doesn't take the OS down with it.

Walk the node: two roles in one process (combined mode), three named listeners, one data directory. listeners is what the node binds to; advertised.listeners is what it tells clients to connect to. That difference is the #1 connectivity bug, coming up on slide 9.

Bring a cluster to life: one ID, format, start

# once, anywhere $ CLUSTER_ID=$(kafka-storage.sh random-uuid) # on EVERY node, before its first start $ kafka-storage.sh format -t $CLUSTER_ID -c config/server.properties # Docker: the image formats for you from the CLUSTER_ID env var (.env) # check the quorum $ kafka-metadata-quorum.sh --bootstrap-server $BS describe --status
ClusterId: Je89w39_Q46DWmFYXCGkGw LeaderId: 1 ← active controller LeaderEpoch: 3 HighWatermark: 182 ← __cluster_metadata position MaxFollowerLag: 0 ← standbys caught up CurrentVoters: [{"id": 1, …}, {"id": 2, …}, {"id": 3, …}] CurrentObservers: []
InconsistentClusterIdException means a node was formatted with a different ID. Wipe that node's log.dirs, re-format with the real ID, and let replication refill it.
Cluster ID is a UUID generated once and stamped into every node's meta.properties. controller.quorum.voters is fixed membership: every node, brokers included, lists every controller. Growing or shrinking the quorum later is a deliberate operation (Module 5). In the lab, the ID lives in labs/module-02/.env.

Topic 1 · Connectivity

"It connects, then hangs": the advertised.listeners trap

Broken Advertises an internal name

Fixed Advertises what the client can reach

Troubleshoot top-down

1Reach bootstrap?

Connection to node -1 → host, port, firewall, security group.

2Reach the leader?

Connection to node 2 after metadata → fix advertised.listeners.

3Protocols match?

Listener security map vs client security.protocol (Module 7).

4Partition healthy?

--describe --unavailable-partitions (slide 12).

① Any broker answers the metadata request. ② The answer contains each leader's ADVERTISED address. ③ The client connects there directly. If that address only resolves inside Docker, the first step works and the second hangs. That's why the lab has two data listeners: PLAINTEXT for containers, EXTERNAL for the host.

Topic 3 · Creating, listing, describing, deleting topics

The topic lifecycle, and the rules that bite

$ kafka-topics.sh --bootstrap-server $BS --create --topic cdr.voice \ --partitions 6 --replication-factor 3 \ --config min.insync.replicas=2 --config retention.ms=604800000 $ kafka-topics.sh --bootstrap-server $BS --list $ kafka-topics.sh --bootstrap-server $BS --describe --topic cdr.voice $ kafka-topics.sh --bootstrap-server $BS --alter --topic cdr.voice \ --partitions 12 $ kafka-topics.sh --bootstrap-server $BS --delete --topic cdr.voice

RF ≤ broker count

RF 4 on 3 brokers fails with InvalidReplicationFactorException.

Partitions only go up

No decrease, and adding partitions remaps keys (Module 1).

Delete is final

Asynchronous and irreversible. No recycle bin, so check the name twice.

Created on purpose

Auto-create is off in the lab. Change configs with kafka-configs.sh (Module 3).

Create returns quickly but partition assignment and leader election happen on the controller. Retention and compaction delete data, never the topic itself. On the shared AWS cluster later, a delete affects everyone: use your own lNN. prefix.
Topic 3 · Describing topics

--describe: the first command in every incident

$ kafka-topics.sh --bootstrap-server $BS --describe --topic cdr.voice Topic: cdr.voice PartitionCount: 6 ReplicationFactor: 3 Configs: min.insync.replicas=2,retention.ms=604800000 Partition: 0 Leader: 2 Replicas: 2,1,3 Isr: 2,1,3 Partition: 1 Leader: 3 Replicas: 3,2,1 Isr: 3,2,1 Partition: 2 Leader: 1 Replicas: 1,3,2 Isr: 1,3,2 Partition: 3 Leader: 2 Replicas: 2,3,1 Isr: 2,3,1 Partition: 4 Leader: 3 Replicas: 3,1,2 Isr: 3,1,2 Partition: 5 Leader: 1 Replicas: 1,2,3 Isr: 1,2,3

Leader: the broker serving reads and writes now.

Replicas: every copy. The first is the preferred leader.

Isr: copies caught up right now. Healthy = same as Replicas.

Health filters · shown with kafka-2 stopped

--under-replicated-partitions

Isr smaller than Replicas. A broker is down or falling behind.

--under-min-isr-partitions

Isr below min.insync.replicas. acks=all writes fail with NOT_ENOUGH_REPLICAS.

--unavailable-partitions

No leader at all. Reads and writes stop for that partition.

$ kafka-topics.sh --bootstrap-server $BS \ --describe --under-replicated-partitions Partition: 0 Leader: 1 Replicas: 2,1,3 Isr: 1,3 Partition: 1 Leader: 3 Replicas: 3,2,1 Isr: 3,1 …
Read the output left to right: leaders are spread 2-2-2 across brokers, replicas list the preferred leader first, and Isr equals Replicas when healthy. The three filters answer "is anything wrong?" for the whole cluster at once; Module 8 turns them into continuous alerts.
Topic 4 · Producing and consuming with the CLI

Console clients are real clients

$ kafka-console-producer.sh --bootstrap-server $BS \ --topic cdr.voice --producer-property acks=all \ --property parse.key=true --property key.separator=: > 966500000001:call-start > 966500000002:call-start
$ kafka-console-consumer.sh --bootstrap-server $BS \ --topic cdr.voice --group billing --from-beginning \ --property print.partition=true --property print.offset=true \ --property print.key=true Partition:3 Offset:0 966500000001 call-start Partition:0 Offset:0 966500000002 call-start

--group = a real group

Offsets are committed and lag is visible. No --group? A throwaway group each run.

--from-beginning

Only applies when the group has no committed offset yet.

Every --producer-property and --consumer-property is a genuine client setting (acks, compression, auto.offset.reset), the same ones the Java apps use in Module 4. Follow the dots: metadata first, then the client talks to the partition leader directly.

Wrap-up

Key takeaways, and a quick self-check

01Page cache over heap

Small heap (~6 GB max), lots of free RAM, dedicated disks, Java 17+.

02Same properties everywhere

server.properties on Linux, KAFKA_* env vars in Docker.

03Format before first start

One cluster ID on every node. Verify with kafka-metadata-quorum.sh.

04Advertise what clients can reach

Separate internal and external listeners. It's the #1 connectivity bug.

05Topic rules

RF ≤ brokers · partitions only increase · delete is async and final.

06Describe first

Leader, Replicas, Isr and the health filters answer "is it healthy?"

No. Partitions only increase. Create a new topic and migrate the data.
